# 隔墙有耳 · Creepy Monitor

网易云的「听歌排行」只画条形图，不写次数。这个油猴脚本把次数补在条形图后面，记住每个人每天新听了多少，并在他人主页附注「我听了 N 次」。

## 一眼看懂

排行接口带上 `type=-1`，能一次拿到「所有时间」和「最近一周」两份榜单，其中「所有时间」那份的 `playCount` 是真实次数，不登录也能请求。网页自己用的是 `type=0` 和 `type=1`，这两条路径的 `playCount` 被服务端清成 0，所以页面上只剩一根光秃秃的条。脚本改走 `-1` 取数，再把每天的快照相减，得到「今天又听了几次」。

- 显示：`46次`、`46次 +3`、`~138次`；周榜标尺太粗、附近又凑不出唯一解释时，退回百分比（悬停里仍写着大约多少次）。页头「累积听歌 N 首」后面还会挂一个 `+2`，那是另一条线，不依赖排行。
- 开销：每个 uid 一条排行请求，缓存几分钟。数据只写 localStorage，不发往任何外部地址。
- 体积：完整版功能齐全；lite 只填次数，代码量小得多。
- 用法：装 Tampermonkey，粘一个文件，打开用户主页的「听歌排行」。

次数可能比你记得的大：单曲循环放一夜，一首歌就能攒下几十上百次。这个数字来自接口返回的真实 `playCount`，脚本只做搬运，不做修正。

## 快速开始

先装 [Tampermonkey](https://www.tampermonkey.net/)（Chrome / Edge）或 Violentmonkey（Firefox）。两个版本功能重叠，装一个就够：

| 版本 | 一键安装 | 源码 | 适合 |
| --- | --- | --- | --- |
| **完整版** | [安装](https://raw.githubusercontent.com/Celeslime/creepy-monitor/master/creepy-monitor.user.js) | [`creepy-monitor.user.js`](https://github.com/Celeslime/creepy-monitor/blob/master/creepy-monitor.user.js) | 次数 + 今日增量 + 我听了 N 次 + 页头新听 + 标尺锚定，全都要 |
| **lite** | [安装](https://raw.githubusercontent.com/Celeslime/creepy-monitor/master/creepy-monitor-lite.user.js) | [`creepy-monitor-lite.user.js`](https://github.com/Celeslime/creepy-monitor/blob/master/creepy-monitor-lite.user.js) | 只填次数，代码量小得多；不做增量也不预取，饱和时直接显示百分比 |

一键安装走 raw 链接；如果打不开，就打开源码页复制全文，粘进 Tampermonkey 新建的脚本里保存。

装完打开用户主页的「听歌排行」：`https://music.163.com/#/user/home?id=xxxxxxx`。

看别人的次数不需要登录；登录只影响「我听了 N 次」，因为它得先知道你是谁。

脚本只读页面上公开的听歌排行，不改动账号、不读取私密数据；登录态只用来确认「我是谁」，取到的数据也只写进本地。

**生效范围**：只在经典版页面生效（存在 `#m-record` 的页面），新版 Web 播放器结构不同。

## 页面上会看到什么

| 页面元素 | 示例 | 含义 |
| --- | --- | --- |
| 次数 | `46次` | 真实播放次数（接口真值，或精确反解） |
| 区间 | `~138次` / `1~2次` | 快照把标尺锁进了窄区间，跨度超过 2 就压成 `~N次`，悬停给出依据 |
| 今日增量 | `46次 +3` | 今天比昨天多听的次数，两个标签页都有 |
| 占比兜底 | `91%` | 标尺太粗、算不出唯一解时的诚实退化，悬停写「按最小可行标尺推大约多少次」 |
| 我听了 N 次 | 行尾小字 | 他人主页上，这首歌你最近一周听过几次 |
| 今天新听 | 页头 `累积听歌 3751 首` 紧跟一个 `+2` | 今天第一次听到的歌有几首（不依赖排行） |

`46次`、`~138次`、`91%` 是同一个位置的三种形态：算得准、锁进区间、退成占比。加上今日增量、「我听了 N 次」、「今天新听」，就是脚本加的全部东西；站点原有文字一个字不动，全部可悬停看依据（数据来源、标尺变化、是否精确）。本人主页官方本来就显示次数，脚本不改写那个数字，只把 `+3` 挂上去，所以两种主页观感一样。

## 数据从哪来

```bash
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=0' # 全部时间
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=1' # 最近一周
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=-1' # 两份一起
```

前两条每条记录长这样：`{ playCount: 0, score, song }`。

第三条返回 `{ allData, weekData }`，`allData` 里的 `playCount` 是真实次数。逐条核对过 `score = floor(playCount * 100 / M)`，`M` 取榜首的次数。

`weekData` 是例外：即使走 `-1`，它的 `playCount` 仍然是 0，只有 `score`。所以「最近一周」这半边还得反解。

`-1` 是网页端自己在用的参数，但清不清零终究由服务端决定。脚本每行先看 `playCount > 0` 才用真值，否则退回反解，哪天这个口子补上了也不用改代码。

## 次数怎么反解

页面模板 `textarea#m-wgt-song-listen` 里写着：

```html
<span class="bg" style='width:${x.score*100/x.max}%;'></span>
{if extData.showCount&&x.playCount}<span class="times f-ff2">${x.playCount}次</span>{/if}
```

条形宽度就是 `score`。「N次」的位置官方留好了，只是 `playCount=0` 时不渲染。脚本直接复用 `.times f-ff2` 这个类，字号和颜色都交给站点 CSS，不自己写样式。

已知一串 `score`、未知 `M`，找最小的 `M` 让每个 `score` 都能被 `floor(100*i/M)` 表达：

```js
for (let M = 1; M <= SAT_MAX; M++) {
  const lat = new Set();
  // i 从 1 起：能进榜就说明本周至少听过一次，0 次不在解空间里
  for (let i = 1; i <= M; i++) lat.add(Math.floor(100 * i / M));
  if (scores.every(s => lat.has(s))) return M;
}
```

`M` 定下来之后，每首歌的次数就是它对应的 `i`，脚本里是一张 `score → 次数` 的反查表。验证过：挑一个没饱和的标尺做盲测，解出的值与真值一致，100 首逐首零误差。

`M` 逼近 100 时格点越来越密，`M ≥ 97` 时步长不到 1.031，0 到 100 基本铺满，任何序列都能命中。所以解出来的值一旦顶到 96 以上，就说明这份榜单已经约束不住标尺了。

## 标尺饱和：「能解出来」不等于「解出来的是真的」

上面那个循环永远能返回一个值，因为 `M` 够大时格点必然铺满；它返回的只是「能解释这份榜单的最小标尺」，真实标尺可能大得多。

判据是这个：**`M0` 往后 10% 以内，还有没有别的标尺也能解释同一份榜单？**

有，说明这份榜单在这个尺度上根本分不出两个值。实测一份真值 127 的榜单：反解给出 89，而 94 也能逐条解释它 —— 两个值只差 5.6%，都在 10% 以内，脚本判为「分不出」，只给百分比。127 其实也解释得通，但判据找不到那么远的解，所以这里不拿它当例子。

10% 这条线是从两头量出来的：完整榜（每首都进榜）时，最近的另一个可行标尺至少差 19%；截断成 top100 的稀疏榜常常只差 1~6%。中间是空的，所以取 10%。

分三条路：

- 格点细、附近也没有第二种解释 → 写次数（`46次`）；
- 手上有先验能把标尺锁进 5% 的窄区间 → 写区间（`~138次`），窄到只差一两个值时直接写开（`1~2次`）；
- 剩下的一律显示 `91%`（占榜首播放量），悬停里给「按最小可行标尺推大约多少次」。

| 真实榜首次数 | 解出的 M | 结果 |
| --- | --- | --- |
| 20 / 40 / 60 / 80 | 一致 | 次数可信 |
| 89 / 127 | 89 | 附近还有 94 能解释，只给百分比 |
| 100 / 300 / 3000 | 97~100 之间某个数 | 与真值无关 |

真实值一定是可行解，所以解出的 `M` 是个严格下界。

## 四条证据求交

每次观测，脚本手上有一堆证据，各自只说「`M` 落在哪一段」，最后取交集。硬证据互相矛盾就整条放弃；软证据跟硬结论冲突时丢掉它，而不是反过来改硬结论。

| 证据 | 区间 | 硬？ | 来源 |
| --- | --- | --- | --- |
| 格点反解 | `[M0, ∞)` | 硬 | 真实标尺一定让每个 `score` 都能命中 |
| 榜首的终身累计 | `[1, 终身次数]` | 硬 | 本周次数不可能超过一生累计 |
| 榜首缺席全时间榜 | `[1, 榜尾值]` | 硬 | 榜固定 100 条，缺席等于终身不到榜尾 |
| 最近 7 天的累加 | `[和, ∞)` | 软 | `days` 里那串日增量 |
| 播放不倒退 | `[hard, ∞)` | 软 | 昨天的次数减去窗口滑出量 |
| prior 命中段 | `[lo, hi]` | 软 | 没动过的那批歌，prior 就是本周次数 |

`hard` 是「昨天这首歌本周是 `c`，今天窗口滑走了最老的一天，今天至少还有 `c` 减去滑走量」推出来的：代进 `s = floor(100c/M)` 得 `M > 100·prior/(s+1)`，逐首取最大，`prior` 先减 1 兜住差分踩点的误差。一首昨天 12 次、今天显示 `0%` 的歌直接说明 `M > 1200`。

「榜首的终身累计」和「榜首缺席」这两条最有用的地方是证伪：某首歌本周被算成 175 次、终身却连榜尾的 56 次都不到，那就说明尺子放大了，而不是歌听得多。

求交之后按这个顺序取值：

1. 反解在饱和线以下（`M0 < 96`）→ 用 `M0`，但先跑一遍上面的 10% 判据，判为歧义就加 `loose` 标记、只给百分比；
2. 交集能收窄到 5% 以内 → 用这个区间，区间里逐首取 `prior`（落在带里就说明今天没动）。候选按「具体程度」排：命中段优先，锚定次之，纯下界最后；
3. 收不窄、但上次存的 `M` 落在交集里而且能解释今天的榜单 → 沿用上次的尺子；
4. 都不行 → 拿交集下界当点估计，明说只是下界。

**沿用只排在第 3 位，这一点是拿 bug 换来的。** 反解能定住标尺时它就是硬下界，真实值不会比它小，让沿用去顶它就再也纠不回来：判据「旧值还能解释今天的榜单」对放大的尺子永远成立（可行集本来就是 `[M, ∞)`），一把被写错的 `M` 会借着它一路传下去。踩过的坑是一把 56 被存进快照后每天自洽地沿用，而真实值只有 28。

反过来，一次观测往往只定得住一段 `[M, M']`，每天各挑各的最小值，同一首歌的次数就会随榜单稀疏度上下跳（先偏小、隔天又偏大，凭空多出几十次）。所以反解不可辨识时，一把稳定的旧尺子比一把可能更准但会飘的新尺子有用 —— 这就是第 3 条存在的理由。

用先验推出来的下界如果越过了硬上界，说明错的是先验，那一条路整段放弃，不拿它去 pin 标尺 —— 否则一把错尺子会被自己的先验反复确认，再也下不来。

这套结构的好处是**加证据不用再改别人**：以后想到新约束，就是多交一个区间，不用回头调顺序。`resolveWeek` 返回的 `scale.why` 记着这次走了哪条路（`solve` / `lock:pin` / `lock:anchor` / `lock:prior` / `prev` / `lower`），出问题时先看它。

## 锁定的输出形态

| 情形 | 输出 |
| --- | --- |
| 多数 prior 能对上，区间窄 | `~138次`，悬停写 `M=136~141`，逐行还带自己的区间 |
| 窄到只差一两个值（低分档常见） | 直接写开：`1~2次` |
| 全员都在 0~1%，没有中段证据 | 凑不出命中段，退回百分比 |
| 今天大半的歌都在涨，prior 不再等于次数 | 一票判不了，退回百分比 |
| 中间漏过一天，或没有快照 | 滑走量算不全，退回百分比 |

`~N次` 里那个 `N` 不是区间中点，而是这首歌「昨天那个次数」（`prior`）落在带里就取它 —— 意思是「大概率没动」。跨度不超过 2 才逐个写开。

低分档单独说一下：能进榜就说明本周至少听过一次，`score=0` 不等于 0 次。榜首一周 137 次时，0% 档只能是 1 次，区间收成一个点。只有榜首特别高（比如一周 500 次）时，0% 档才会是 `1~4` 次。

只取「最小可行 M」会被稀疏的 `score` 骗：真实 500 次、但 `score` 只落在 100/50/20/10/5 时，会解出 20 并且当成准确值。现在硬下界先把它证伪（`prior` 一对，20 明显不够），再重新锁定。

模拟过一次：60 首静止歌曲加 1 首从 40 次被刷到 137 次的歌，锁定到 `M=136~138`（命中段两端各留 1 次），60 行全部补上次数，被刷那首算出的 `+97` 与真值一致。

## 今日增量

`+3` 是两份快照相减得来的。两份榜单的 top100 交集很低，大部分歌只出现在其中一份；只算一份，另一个标签页就会空掉，所以两份都算：

| 来源 | 覆盖 | 精度 |
| --- | --- | --- |
| 全时间榜 `playCount` 真值差分 | 「所有时间」那 100 首 | 精确，两个真值直接相减 |
| 周榜反解差分 | 「最近一周」里不在全榜的歌 | 受 7 天滑窗和标尺饱和影响 |

同一首歌两边都有时取真值。周榜那份要补偿滑窗：

```
D_d = (W_d - W_{d-1}) + D_{d-7}
```

7 天前那天的增量已经滑出窗口，得加回来，这也是历史要留 8 天而不是 7 天的原因。合并后只有一张增量表，切标签页不会掉 `+n`。

补偿项有个硬约束：昨天的窗口必然包含 7 天前那一天，所以昨天的累计不可能小于那天的增量。小于就说明昨天的反解偏小了（标尺粗的时候，2 次和 3 次落在同一个 `score` 上），脚本拿那天的增量当昨天的下界再相减，否则那几首会被整个加回来，冒出「本周 2 次、今日 +3」这种自相矛盾的值。

能不能干脆不要补偿项？试过（用 `--script` 换一份把 `comp` 置空的实现，跑同一批观测）：整体平均误差反而从 0.06 降到 0.05。但这是分母在骗人 —— 99% 的周榜行「7 天前根本没听」，补偿本来就是 0，去掉它对这些行毫无影响，却把它们摊进了平均。只看 7 天前听过的那批行，去掉补偿会系统性少算 **0.41 次/行**，三个画像一致、方向恒定（带符号偏差从约 −0.03 掉到 −0.41）。而页面上你盯着的正是这几首常听的歌。代价还有一条：`exact` 依赖补偿项存在，去掉之后所有的 `+n` 都退成 `~n`，「确定」这一档整体消失。

唯一例外是 heavy 画像：榜首的格点粗到一格超过一次，补偿的 ±1 噪声开始盖过它的贡献，那批行的绝对误差 0.57 反而高于不做补偿的 0.41。但这是拿 0.4 的系统性偏差换一点方差，不划算。

新进榜的歌没有基线。周榜那份拿「本周累计」当今日增量，严格说是上限，但新进榜多半就是今天才开始听，值通常等于当日，悬停里写明「今日上限」。全时间那份的累计是一生的，拿 0 当基线能报出几百次，所以这类直接跳过。

还有一层：听得越杂，榜单越满。一周听过 100 首以上时，100 个位置装不下，新听的那首要排在 101 名之后，等别的歌滑出窗口才挤进来。可能过两三天才出现在榜上，脚本把它当「新进榜」，给的「本周累计 1 次」其实是几天前听的。这类账号的今日增量会系统性偏大一点，多出来的就是积压之后才进榜的那几首。接口只给前 100 名，看不到就算不出来，这部分只能认。

升级当天，全时间基线是空的（旧版本只存过周榜），这一页当天算不出增量，悬停写「基线今天才建立」，第二天恢复。

标尺每晚重解一次，换了尺子是不是就不能相减，取决于那天的次数定没定死。区间退化成一个点，说明那天是精确反解，每首歌的次数就是真实次数本身 —— 榜首今天多听了 7 次把 `M` 从 29 顶到 36，别人的次数并不因此改变，相减照样成立，只是那一格可能差一次，悬停里写「标尺从 29 变成 36，可能差一格」。只有靠先验锁在一段区间里的标尺（`lo ≠ hi`），次数本身不唯一，才整段跳过并记进 `dirty`（7 天后的滑窗补偿会缺这一块）。旧存储没有 `sc` 字段时，既拿昨天快照里的最大值当它的标尺，也当作「定没定死不可知」，保守地按跳过处理。

精度标记只有四个条件同时满足才算 `exact`：7 天前那天的增量在手、基线到今天约一天、最近 8 天没漏访、两次观测用的是同一把尺子。「约一天」这条要看时间戳而不是日历天 —— 一天看两次时，头一次离昨天最后那次可能只有十来个钟头，而补偿项是一整天的量，多出来的半天会被算进今天。23:50 和次日 00:10 之间只隔 20 分钟，日历天却翻了一页，所以脚本给每份快照记了时间戳，要求落在 24 小时 ±3 小时之内。旧存储没有时间戳时退回只看日历天。漏一天之后那条链路会带一份固定偏差，数学上补不回来，只能等 8 天后自然清掉。

## 我听了 N 次

只在他人主页行尾，回答「这首我也在听吗」（不是「我总共听过几次」）。流程：问 `/api/nuser/account/get` 确认身份（未登录直接跳过）→ 拉自己的周榜按歌曲 id 比对。最多两条请求，排在首屏之后，与排行请求共用一条串行队列。自己主页不显示这一段，那栏本来就是真数。

这份周榜必须单独取 `type=1`：排行缓存走 `type=-1`，其 `weekData.playCount` 恒为 0，混用会一首歌都取不到。id 对不上时再按「歌名 + 首位歌手」认一次 —— 同一场录音常挂两个 id（单曲版 / 专辑版），只按 id 会整行空着。

## 今天新听了 N 首

页头那行「累积听歌 3751 首」是注册以来听过多少首**不同的歌**（按歌计、不按次数，只增不减）。把上次记下的值留下来相减，差值就是这期间第一次听到的歌有几首。数字直接读页面那行文字，不额外发请求；接口里同一个值叫 `listenSongs`，只用来核对语义。

它和排行差分互不相干：排行只给 top100，这一条不挑歌，能回答「今天碰到几首没听过的」。头一天只存基线不显示；同一天再看会跟着变大；隔几天才来看则摊成那几天的合计（悬停写明天数）。

## 刷新机制

- **抢先注入**：列表没渲染时就按 URL 里的 uid 发请求，不等 DOM；画上后靠轮询兜底（首屏前密、画完放慢）。
- **重画恢复**：切标签页列表会重渲染，脚本靠 uid、条目数、首行 HTML 和**注入痕迹**组成的标记发现变化，下一轮补上。痕迹是为「列表被重画回原样」准备的：行数首行都没变、只有数字没了，不带痕迹会误判成处理过。这里刻意没用 MutationObserver，轮询 + 标记比对更稳。
- **标签页识别**：不靠 DOM 判断，拿两套数据的 score 和条形实际宽度比误差，小的胜出。

## 配置

脚本顶部的 `CFG`：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `MODE` | `'auto'` | `auto` 能反解就给次数，饱和时先锁标尺、锁不住退百分比；`count` 总是给次数（饱和时给下界）；`percent` 总是给百分比 |
| `DAILY` | `true` | 是否记录并显示今日增量（页头「今天新听」也归它管） |
| `SHOW_MINE` | `true` | 他人主页行尾是否附注「我听了 N 次」 |
| `ASSUME_TOP_COUNT` | `0` | 设成正数则按「榜首 = N 次」换算成 `~N次` 并给出区间 |

其余是节奏参数：首屏与刷新轮询间隔、取「我听了 N 次」前的延迟、缓存时长、请求最小间隔、失败退避、账号上限。默认值都在脚本顶部，一般不用动。`DEBUG` 打开会在控制台打印判定过程。

算法常量（不建议改）：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `SATURATION` | 96 | 反解必然失效的分界 |
| `DENSE` | 91 | 格点粗到可能误导的分界 |
| `AMBIGUOUS` | 0.1 | `M0` 往后多近还有别的解释就不算解出来 |
| `SAT_SLACK` | 0.05 | 区间窄到多少才算锁定，兼作跨天标尺容差 |
| `SAT_MAX` | 2000 | 一周次数的搜索上界 |

## 隐私与本地存储

- **数据只写 localStorage**（键 `tm_w163_daily_v1`），**不发往任何外部地址**。
- 只读页面上公开的听歌排行；登录态只用来确认「我是谁」。
- 每个 uid 一条排行请求，缓存几分钟。

顶层 `{ v, users }`，`users` 按 uid 存：

| 字段 | 内容 |
| --- | --- |
| `cur` / `base` | 今天和昨天的快照，各含周榜反解值 `week`、全时间真值 `all` 和观测时间戳 `t` |
| `days` | 按日期存的合并日增量（留 8 天） |
| `head` | 页头累计听歌数的上次记录：`base` 是上次跨天时的值，`n` 是最近一次看到的值 |
| `dirty` | 漏访或标尺漂移的标记，用来判断当天算不算精确 |
| `seen` | 最后访问时间，淘汰老账号用 |
| `sc` / `w` | 当天用的标尺 / 估算误差半径（下次当先验先扣掉，免得误差放大） |

单人十几 KB（8 天 × 最多 100 首 + 两份快照）。账号数超过 `MAX_USERS`（默认 60）后淘汰最久未访问的。从 3.4 之前的版本升级会就地翻译旧格式，历史不丢；想重新校准，删掉这个键重新预热即可（但删了 `days` 会让滑窗补偿残一周）。

## 已知限制

| # | 限制 | 性质 |
| --- | --- | --- |
| 1 | 「最近一周」的绝对次数仍是反解出来的 | `weekData` 的 `playCount` 恒为 0，只能从 `score` 推；「所有时间」不受影响 |
| 2 | 漏一天访问会污染周榜那条按天相减的链路 | 误差系数恒为 1，不衰减，数学上补不回来，脚本用 `exact` 标记提示。全时间走真值差分，不受影响 |
| 3 | 两份榜单都只给 top100 | 掉出前 100 的歌拿不到次数，这天的增量会漏 |
| 4 | 量化分辨率是 `M_w / 100` | 一周榜首 200 次时，听 1 次仍落在 `score=0`，看不出来 |
| 5 | 周榜 `M_w ≥ 91` 要靠历史快照或榜首的终身累计救 | 两条路都不通（头一回访问、中间漏天、榜单不满 100 条且榜首缺席）就只剩百分比 |
| 6 | 次数可能偏小，不会偏大 | 榜单 `score` 稀疏时反解只能给出下界（最小可行 `M`），拿它算的次数是保守值；偏小只是少报，不会凭空多出几十次 |
| 7 | 标尺跳变那天可能差一格 | 两天都是精确反解时照常相减，但格点变了，某首歌的差值可能多算或少算一次；悬停会说明标尺从多少变成多少。要是两天的次数都只锁在区间里（`lo ≠ hi`），这天仍然整段空着，滑窗补偿链因此有一周是残的 |
| 8 | 「我听了 N 次」只覆盖最近一周，且只在你周榜 top100 内 | 它回答「这首我也在听吗」，不是「我总共听过几次」；榜单外没有任何接口能查到，同名版本靠歌名认，标题一样歌手一样但其实是另一段录音时可能认错 |
| 9 | 只在经典版页面生效（存在 `#m-record`） | 新版 Web 播放器结构不同 |
| 10 | 今天新进榜的歌给的是上界 | 昨天没有基线，「本周累计」可能含前几天的播放；全时间榜新进的直接跳过 |
| 11 | 听得杂的账号，新歌要排队进榜 | 一周听过 100 首以上时榜单装满，新听的那首要等别人滑出窗口，可能晚几天才上榜；那几次会记到进榜那天，今日增量因此偏大 |
| 12 | 「今天新听」要连着看才有值 | 头一天只存基线；隔了几天才来看，差值摊成那几天的合计，悬停里写明天数。它读的是页头那行文字（`#rHeader h4`），站点改排版就失效 |
| 13 | `M` 越大能显示次数的人越少 | `M ≥ 91` 的账号（一周榜首听九十多次以上）几乎全程显示百分比，只有先验恰好把标尺锁进窄区间时才给数。这是信息量的天花板：榜单在这个尺度上分不出两个值，硬给数字就是编。仿真的 heavy 画像里 2100 行只有 200 行拿到次数 |
| 14 | 偶尔一整天的次数全偏小 5~10% | 锁定时用的 prior 本身是估的，命中段可能整体偏一格。区间两端各留了 1 次余量，`npm run sim` 的 150 个虚拟账号里没有一行越界，但真碰上极端稀疏的榜单仍可能差几次 |
| 15 | 观测间隔不是 24 小时时，增量的精度会掉 | 补偿项 `days[today-7]` 是一整天的量，而周榜是最近 168 小时的滚动窗口 —— 只有两次观测正好隔 24 小时、落在同一个钟点，滑出去的那一块才等于它。小时级仿真里，24 小时一次平均差 0.05 次/行，12 小时一次 0.19，6 小时一次 0.24。脚本只能把「不算精确」标出来，修不了 |
| 16 | `exact` 说的是「算术链对得上」，不是「精确到次」 | 钟点固定、对齐误差为 0 时，声称精确的行里仍有约 1.4% 差 1~3 次，集中在 heavy 画像。`score` 只有 0~100 的整数格点，榜首周榜过百时一个格点就超过一次，单曲的 ±1 在分数上根本看不见；补偿项本身也是上一轮估出来的数，链条上带着一次格点误差 |

## 测试

纯 Node，不需要浏览器。`npm run verify` 提交前全跑。

| 命令 | 覆盖 |
| --- | --- |
| `npm test` | **205 条断言、13 个套件**：DOM 注入结构、滑窗补偿、标尺决策、标尺歧义、标尺跳变、锚定上界、页头计数、「我听了 N 次」、同名异 id、重画补回、真实快照回放、同日重访时序、两版纯函数一致性 |
| `npm run sim` | **随机仿真**：造虚拟账号 → 按站点公式生成榜单 → 逐日喂给脚本 → 拿「我让它听了几次」当标准答案 |
| `npm run sim:hourly` | **小时级仿真**：被观察者按小时听歌、观察者每几小时刷新一次，专门压增量那条链路（`--window rolling\|day` 切换周榜窗口模型） |
| `npm run verify` | 三个都跑 |

### 仿真的三条硬约定

1. **只要页面写成「N次」，就必须真的等于 N**（`≥`、`~`、`%` 不在此列）；
2. 写成 `a~b次` 的，真值可以落在区间外 5% 以内（两端都是估的），超出去算错；
3. `今日增量 ≤ 本周累计` 这类不变式，任何画像下都不能破。

第 1 条是这套测试最值钱的地方：**它不认「大约对」，只认「确实对」**。默认 6 账号 × 24 天 0.3 秒跑完，四个画像（casual / normal / wide / heavy）加随机漏访。

```bash
node test/sim.js --accounts 20 --days 40 --seed 7 --verbose
node test/sim.js --dump 24 # 打印那天周榜的 score 序列，离线复现某一行
npm run sim -- --accounts 6 --days 30 --seed N

node test/sim-hourly.js --every 6 --jitter 0.6 --window rolling
node test/sim-hourly.js --trace # 逐次打印观测时序
node test/sim-hourly.js --lag 3 # 榜单延迟 3 小时才可见
node test/sim-hourly.js --script /tmp/x.js # 换一份脚本跑同一批观测（A/B）
```

### 小时级仿真在压什么

`sim.js` 的时间轴是一天一格：听一天、看一次，等价于假设「每次观测都正好隔 24 小时、
落在同一个钟点」。真实用法不是这样，`sim-hourly.js` 把时间轴拆到小时：被观察者按
一天里真实的作息分布听歌，观察者隔几小时才打开一次。

它压出来的三件事：

1. 同一天第二次观测如果没算出周榜，整表覆盖会把上午已经算好的增量抹掉。现在只补
   缺失的行，不覆盖新值（v3.8.1）。
2. 悬停里「跨了 0 天」——同一天重访时 `gap` 是 0，但差值仍是从基线那天算起的。改成用
   基线算出的 `baseGap`（v3.8.1）。
3. `exact` 的时间闸门：一天看两次时，头一次离昨天最后那次可能只有十来个钟头，而补偿
   项是一整天的量。现在要求两次观测的时间戳落在 24 小时 ±3 小时之内（v3.8.1）。

周榜是**最近 168 小时**的滚动窗口（2026-11-17 确认）。这决定了补偿项什么时候才成立：
`D = W_cur − W_base + days[today-7]`，只有两次观测正好隔 24 小时、落在同一个钟点，
滑出去的那一块才正好等于 `days[today-7]`。看得越勤越对不上 —— 滚出去的是 6 个小时的
量，脚本手上只有整天的量。

| 观测间隔 | 周榜行平均绝对误差 | 声称精确却算错 |
| --- | --- | --- |
| 24h（钟点固定） | 0.05 | 39 |
| 24h（±25% 抖动） | 0.12 | 47 |
| 12h（±60%） | 0.19 | 57 |
| 6h（±60%） | 0.24 | 164 |

（6 个账号 × 40 天。`--window day` 只当对照组：自然日窗口下补偿项跟观测钟点无关，
12 小时一次也能做到 0.12。）

24 小时那一档剩下的误差不是窗口错位。钟点固定时对齐误差是 0，仍然错 39 行，而且全部
差 1~3 次、集中在 heavy 画像 —— 是 `score` 的整数格点太粗：榜首周榜过百时，一个格点就
超过一次，单曲的 ±1 在分数上看不见。所以 `exact` 保证的是「算术这条链对得上」，不是
「这个数字精确到次」。

`test/fixtures/snapshot-169.json` 是 2026-11-14 那次「整页增量消失」的现场（裁掉了与结论无关的字段），`test/replay-169.js` 拿它当回归语料：改了标尺或差分逻辑，这里必须仍然算出那六行、合计 +20 次。

> 饱和区那批偏差曾是 `--strict` 的靶子（627 行把估算写成精确值）。v3.8 的 10% 判据落地后降到 **0**，25 个种子（150 个账号）零违规 —— 代价是 heavy 画像里 2100 行只剩 200 行拿到次数，其余显示百分比。这是刻意的取舍：宁可不给数，不给假数。
