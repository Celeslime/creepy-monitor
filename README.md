# 隔墙有耳 · Creepy Monitor

一个 Tampermonkey / Violentmonkey 用户脚本：在网易云音乐网页版的**用户主页「听歌排行」**里，为每首歌补上播放次数，并在你每天访问时自动维护一份「今日新增」记录。

别人的主页默认只给你看一根条形图。这个脚本把条形图背后的数字挖出来。

> 名字是玩笑，代码不是 —— 只读你登录后网页版自己就在请求的公开数据，不写账号，不上传任何东西。

---

## 效果

脚本会在每行的播放条右侧插入一个数字，按数据可信度分三种状态：

| 显示 | 含义 | 出现条件 |
| --- | --- | --- |
| `46次` | 精确次数 | 格点反解得到唯一标尺，或本人主页（接口直接返回真数） |
| `46次 +3` | 精确次数 + 今日新增 3 次 | 已积累足够历史，差分链路干净 |
| `91%` | 占榜首播放量的百分比 | 反解标尺饱和，绝对次数不可还原 |

鼠标悬停可以看到具体口径（真实数据 / 格点反解 / 估算）。

## 安装

1. 安装 [Tampermonkey](https://www.tampermonkey.net/)（Chrome / Edge）或 Violentmonkey（Firefox）
2. 点这个链接一键安装：[**creepy-monitor.user.js**](https://raw.githubusercontent.com/Celeslime/creepy-monitor/master/creepy-monitor.user.js)，脚本管理器会直接弹出安装页；或新建脚本，把文件内容全部粘进去保存
3. 打开任意用户主页，例如 `https://music.163.com/#/user/home?id=xxxxxxx`，切到「听歌排行」

需要登录态。未登录时接口仍返回数据，但「本人真实次数」不可用。

## 原理

### 1. 数据来源

网页版听歌排行用的是这个接口，无需额外签名：

```bash
# 所有时间
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=0'
# 最近一周
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=1'
```

返回 `allData` / `weekData`，每项形如：

```json
{
  "playCount": 0,
  "score": 93,
  "song": { "id": 411315632, "name": "丑", "ar": [] }
}
```

关键点：**`playCount` 只对本人返回真值，对他人恒为 `0`**（带登录 cookie 请求也一样）。他人只能拿到 `score`。

### 2. score 是什么

页面模板（`textarea#m-wgt-song-listen`）里写得很直白：

```html
<span class="bg" style='width:${x.score*100/x.max}%;'></span>
{if extData.showCount&&x.playCount}<span class="times f-ff2">${x.playCount}次</span>{/if}
```

条形宽度就是 `score`。官方本来就有「N次」这个位置，只是他人页面 `playCount=0` 所以不渲染 —— 这也是本脚本复用 `.times f-ff2` 类、不自己写样式的原因。

用本人账号的真实数据反推，可以确定归一化公式：

```
score = floor(playCount * 100 / M)      # M = 榜首真实次数
```

验证方式：取本人 `allData` 的 100 条真数逐一比对，`floor` 100/100 吻合，`round` 有 81 条不符。

### 3. 格点反解

已知 `score` 序列、未知 `M`，问题变成：找一个 `M`，使所有 `score` 都能被 `floor(100*i/M)` 表达。

```js
for (let M = 1; M <= 100; M++) {
  const lat = new Set();
  for (let i = 0; i <= M; i++) lat.add(Math.floor(100 * i / M));
  if (scores.every(s => lat.has(s))) return M;   // 最小的可行 M
}
```

`M` 同时给出每首歌的次数：`count` 就是该 `score` 对应的 `i`。

盲测（只用 `score`，不看 `playCount`）：

```
真实 M = 49 | 反解 M = 49 ✓
逐首次数完全一致: 100/100
```

### 4. 饱和定理：为什么有时只能显示百分比

当 `M ≥ 97` 时，格点步长 `100/M ≤ 1.031`，`floor(100*i/M)` 会覆盖 `0..100` 的全部整数。于是：

- 任何 `score` 序列都能被 `M ≥ 100` 表达，解集是连续区间 `[minM, ∞)` 而不是有限个解
- 反解结果恒定落在 `97~99`，与真实值无关

模拟 200 次/档，命中率：

| 真实榜首 | 反解输出 | 命中率 |
| --- | --- | --- |
| 20 / 40 / 60 / 80 | 20 / 40 / 60 / 80 | 100% |
| 100 | 99 | 1% |
| 300 | 99 | 0% |
| 3000 | 99 | 0% |

所以脚本用 `SATURATION = 96` 做分界：低于它显示次数，高于它退回百分比。这个分界不是拍脑袋，是上面这个步长推导出来的。

`M` 同时是严格下界（真实值必然也是可行解），所以饱和时 tooltip 会给出 `≥97次` 这样的下限，但不会把它伪装成精确值。

### 5. 今日增量

周榜是最近 7 天的滑动窗口。记 `W_d` 为第 d 天观测到的「该歌本周总次数」，`D_d` 为当天新增：

```
W_d = Σ D_{d-k}          (k = 0..6)
W_d − W_{d-1} = D_d − D_{d-7}
⟹ D_d = (W_d − W_{d-1}) + D_{d-7}
```

「7 天前那天的播放」会滑出窗口，所以必须把它加回来 —— 这就是要保留 **8 天**历史（`today-7 … today`）的原因，而不是 7 天。

周榜标尺比年榜小得多（实测某人一周榜首仅 2 次），反解几乎总是精确：

```
周榜 29 首 | 反解 M = 2 | 真值 M = 2 | 逐首吻合 29/29
```

模拟 20 天连续访问：57/57 全中，第 8 天起进入精确模式。

## 配置

脚本顶部的 `CFG`：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `MODE` | `'auto'` | `auto` 自动降级 / `count` 总是显示反解值（饱和时 `≥N次`）/ `percent` 总是百分比 |
| `DAILY` | `true` | 是否维护并显示今日增量 |
| `ASSUME_TOP_COUNT` | `0` | 设为正数则按「榜首 = N 次」换算成 `≈N次`，并给出区间 |
| `REFRESH_MS` | `800` | 轮询间隔，只读两个 DOM 节点 |
| `CACHE_MS` | `60000` | 同 uid 接口结果缓存 |
| `MAX_USERS` | `60` | 日增量记录的人数上限，超出按最久未访问淘汰 |
| `DEBUG` | `false` | 控制台输出判定过程 |

## 数据存储

只存在浏览器 `localStorage`，键名 `tm_w163_daily_v1`，不上传任何地方：

```json
{
  "v": 1,
  "users": {
    "1384117962": {
      "cur":   { "day": "2026-10-29", "counts": { "411315632": 3 } },
      "base":  { "day": "2026-10-28", "counts": { "411315632": 2 } },
      "days":  { "2026-10-28": { "411315632": 2 } },
      "dirty": "2026-10-15",
      "seen":  1793276935491
    }
  }
}
```

单人占用约 10KB（8 天 × ≤100 首）。想重新校准，删掉这个键即可，会重新走 7 天预热。

## 已知限制

1. **他人绝对次数无法还原。** 不是精度问题，是数据里没有：`playCount` 对他人恒为 0，`score` 只有 100 级分辨率，且 `M` 被归一化抹掉。
2. **漏一天访问会永久污染该「星期几」链路。** 每天的增量建立在 7 天前那个格子的值上，误差系数恒为 1，不会衰减。实测漏一天后平均每首每日误差 0.32 次。这是信息缺失的代价，数学上不可修复 —— 脚本用 `exact` 标记显式提示。
3. **周榜 top100 截断。** 掉出前 100 的歌拿不到次数，差分时按 0 处理并钳正，这部分增量会漏。
4. **量化分辨率 = M_w / 100。** 一周榜首 200 次时，1 次播放落在 `score = 0`，不可见。
5. **周榜 `M_w ≥ 96` 时不记录。** 标尺饱和，次数不可信。
6. 只在经典版页面（存在 `#m-record`）生效，新版 Web 播放器结构不同。

## 自己验证

想复核文中结论，最可靠的方式是用**自己的账号**：本人主页的接口会返回真实 `playCount`，可以作为 ground truth。

```bash
# 1. 从浏览器复制 Cookie，取 MUSIC_U 即可
curl 'https://music.163.com/api/v1/play/record?uid=<你的uid>&type=0' \
  -H 'Cookie: MUSIC_U=<你的token>'

# 2. 用返回的 score 跑格点反解，与 playCount 对比
```

连续观察 8 天，把「反解出的日增量」和「真实 playCount 的差分」并排比对，就能量出这套管线的实际误差 —— 比任何模拟都可信。

## 版本沿革

| 版本 | 时间 | 做法 |
| --- | --- | --- |
| v1.0 | 2020-05 | 从条形宽度按整数百分比反推，循环上限 100 |
| v2.3 | — | 同上，重写并修掉 observer 抖动 |
| **v3.2** | 2026-10 | 改走接口取 `score`；加入饱和判定与今日增量 |

旧版本归档在 [`legacy/`](./legacy)，含 2020 年的原始实现（曾发布于 [Greasyfork](https://greasyfork.org/zh-CN/scripts/403084)，那个页面**已不再维护**，请以本仓库为准）。它们的问题在 v3.2 里已由「饱和定理」解释清楚：`M ≥ 97` 后反解必然退化成常数 97~99。

从 v1.0 到 v3.2 隔了六年。中途停更的原因很简单：不管怎么改代码，`playCount` 都不会从接口里长出来，只能在错误的前提上反复调参。真正解决问题的不是重写，而是先花半小时把接口和页面模板读明白，确认「别人的绝对次数根本不存在」。
