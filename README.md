# 隔墙有耳 · Creepy Monitor

在网易云音乐网页版的**「听歌排行」**里，把每首歌的播放次数补出来，并记录每天新增了多少次。

别人的主页只给你看一根条形图。这个脚本把条形图背后的真实播放次数挖出来 —— 一个接口参数的事，但藏了六年。

`网易云音乐` `听歌排行` `播放次数` `Tampermonkey` `userscript` `油猴脚本`

> 名字是玩笑，代码不是：只读你登录后网页版本就在请求的数据，不写账号，不上传任何东西。

## 效果

| 显示 | 含义 | 出现条件 |
| --- | --- | --- |
| `46次` | 真实播放次数 | 「所有时间」标签页：接口直接返回真数；「最近一周」标签页：格点反解 |
| `46次 +3` | 今天又听了 3 次 | 昨天有这个基线；两个标签页通用 |
| `46次` ＋ 行尾 `我听了 2 次` | 你自己最近 7 天也听了 2 次 | 他人主页、已登录、这首在你周榜 top100 内 |
| `91%` | 占榜首播放量的百分比 | 周榜反解标尺饱和（一周榜首 ≥96 次的重度用户） |

本人主页官方本来就有次数，脚本不改写它，只把 `+3` 挂进官方数字里，所以两种主页观感一致。自己主页不显示「我听了 N 次」—— 那里的数字原本就是真的。

悬停能看到口径：真实数据 / 格点反解 / 估算区间。

**速度**：接口在页面加载时就发出，不等列表渲染；数字通常比列表晚 20~50ms 出现。模拟环境（接口 150ms、列表 400ms）实测约 30ms，而「等列表出现才请求 + 800ms 轮询」的老写法约 600ms。

**开销**：整个页面只发 **1 个**排行请求（`type=-1` 一次返回全部时间 + 最近一周），请求串行、间隔 ≥300ms，避开网页自己的那条；数据缓存 5 分钟，切标签页、进出同一主页都不再请求。早期版本是 2 个请求同时发，会跟网页争夺配额，把页面自己的排行榜挤掉。

| [`creepy-monitor.user.js`](./creepy-monitor.user.js) | 584 | 次数 + 今日增量 + 我听了 N 次 + 请求节流 |
| [`creepy-monitor-lite.user.js`](./creepy-monitor-lite.user.js) | 107 | 只有次数 |

lite 是「我不需要那么多」的那个：一个请求、两个标签页都能填、饱和时退成百分比。去掉注释和空行只有 **74 行**，和 2020 年的 v2.3 同一个体量。它不做增量、不做「我听了 N 次」、不发第二条请求 —— 只想看一眼次数就装它。

## 安装

1. 装 [Tampermonkey](https://www.tampermonkey.net/)（Chrome / Edge）或 Violentmonkey（Firefox）
2. 新建脚本，粘贴 [`creepy-monitor.user.js`](./creepy-monitor.user.js) 全文保存
   或点 raw 链接（若 `raw.githubusercontent.com` 访问不了就用上一种方式）：
   `https://raw.githubusercontent.com/Celeslime/creepy-monitor/master/creepy-monitor.user.js`
3. 打开用户主页（`https://music.163.com/#/user/home?id=xxxxxxx`），切到「听歌排行」

别人的次数不需要登录（`type=-1` 对匿名请求也返回真值）。登录只影响「我听了 N 次」那一段 —— 它要问「我是谁」。

## 原理

### 数据从哪来

```bash
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=0'   # 全部时间
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=1'   # 最近一周
```

每条形如 `{ playCount, score, song }`。这里有个藏得很深的分叉：

```bash
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=-1'
```

`type=-1` 会**同时**返回 `allData` 和 `weekData`，而且 —— 对任何人（不需要登录）—— `allData` 里的 `playCount` 是**真实播放次数**。实测 4 个账号（榜首 2 / 49 / 397 次）公式 `score = floor(playCount*100/M)` 全部 100% 吻合。

而 `type=0` / `type=1` 这两条「正规」路径会把 `playCount` 清成 `0`。也就是说：**别人的绝对次数一直都在，只是要绕到 `-1` 那个入口拿**。v1.0~v3.3 的所有反解，都是在这个泄漏点之外的死路上绕。

`weekData` 例外：即使 `type=-1`，它的 `playCount` 仍是 `0`，只有 `score`。所以「最近一周」仍要反解（下一节），而周榜标尺通常极小，反解几乎总是精确的。

这个 `-1` 是网易自己的参数（网页端也在用），但清不清零终究由服务端决定，哪天可能被补齐。脚本对此有天然降级：每行判断 `playCount > 0`，没有就退回反解，不需要改代码。

### score 是什么

页面模板 `textarea#m-wgt-song-listen` 里写着：

```html
<span class="bg" style='width:${x.score*100/x.max}%;'></span>
{if extData.showCount&&x.playCount}<span class="times f-ff2">${x.playCount}次</span>{/if}
```

条形宽度就是 `score`。「N次」的位置官方本来就留好了，只因他人 `playCount=0` 而不渲染 —— 这也是脚本直接复用 `.times f-ff2` 类、不自己写样式的原因。

用本人真实数据反推，归一化公式是：

```
score = floor(playCount * 100 / M)      # M = 榜首真实次数
```

验证：本人 `allData` 100 条逐一比对，`floor` 100/100 吻合，`round` 81 条不符。

### 格点反解

> 它只服务 `weekData`：那个标签页显示的次数、以及它那部分今日增量。「所有时间」直接用 `playCount`，不反解。

已知 `score` 序列、未知 `M`，就找那个使所有 `score` 都能被 `floor(100*i/M)` 表达的最小 `M`：

```js
for (let M = 1; M <= 100; M++) {
  const lat = new Set();
  for (let i = 0; i <= M; i++) lat.add(Math.floor(100 * i / M));
  if (scores.every(s => lat.has(s))) return M;
}
```

`M` 同时给出次数：每首歌的 `count` 就是该 `score` 对应的 `i`。盲测（只喂 `score`、不喂 `playCount`）：真实 `M=49`，反解 `M=49`，100 首逐首零误差。

### 饱和：为什么周榜有时只能给百分比

`M ≥ 97` 时步长 `100/M ≤ 1.031`，`floor(100*i/M)` 覆盖 `0..100` 全部整数，于是任何序列都能被 `M ≥ 100` 表达，解集变成连续区间 `[minM, ∞)`，反解结果恒定落在 97~99。

| 真实榜首 | 反解输出 | 命中率 |
| --- | --- | --- |
| 20 / 40 / 60 / 80 | 20 / 40 / 60 / 80 | 100% |
| 100 | 99 | 1% |
| 300 / 3000 | 99 | 0% |

所以分界取 `SATURATION = 96`。这个数不是拍脑袋：`M=97` 起必然全覆盖（退化），`M=96` 时 97 个格点映射不到 `0..100` 的 101 个值，重复已经很密、反解不再可信，于是保守再留一格。真实值必然也是可行解，故 `M` 是严格下界，饱和时 tooltip 给 `≥97次`，但不伪装成精确值。

### 今日增量：两份数据合并成一张表

增量要挂在列表每一行上，而列表有两个标签页，歌却几乎不重合 —— 实测两个账号「最近一周」和「所有时间」的交集只有 **13/100** 和 **4/100**。只靠任何一份单独的榜单，另一页都会空掉，所以两份都算：

| 来源 | 覆盖 | 精度 |
| --- | --- | --- |
| 全时间榜 `playCount` 真值差分 | 「所有时间」那 100 首 | 精确，两个真值直接相减 |
| 周榜反解差分 | 「最近一周」里不在全榜的歌 | 受 7 天滑窗和标尺饱和影响 |

同一首歌两边都有时取真值。周榜那份仍需补偿滑窗：

```
W_d − W_{d-1} = D_d − D_{d-7}   ⟹   D_d = (W_d − W_{d-1}) + D_{d-7}
```

7 天前那天会滑出窗口，必须加回来 —— 这就是要留 **8 天**历史而不是 7 天的原因。全时间那份是真值相减，既不需要补偿，也不受饱和影响。两份合并后只有一张增量表，切标签页不会掉 `+n`。

**新进榜的歌不给增量。** 它昨天不在榜里，没有基线；拿 0 当基线会把一生累计算成今天听的（全时间榜上就是几百次）。宁可这一天不显示。

### 「我听了 N 次」不用猜

`play/record` 对本人返回真实 `playCount`，所以先问「我是谁」（`/api/nuser/account/get`，未登录返回 `account: null`，直接跳过），再拉一次自己的周榜（`type=1`，这条对本人不清零），按歌曲 id 比对就有精确值。

刻意不抢首屏：这两个请求在别人的次数画完之后才开始（`MINE_DELAY_MS`，默认 600ms），并且和排行请求排在同一条串行队列里。换来的是首屏只有 1 个请求在飞 —— 「我听了 N 次」晚一秒出现，但不会把网页的排行榜挤掉。

## 配置

脚本顶部 `CFG`：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `MODE` | `'auto'` | `auto` 自动降级 / `count` 总显示反解值（饱和时 `≥N次`）/ `percent` 总显示百分比 |
| `DAILY` | `true` | 是否维护并显示今日增量 |
| `SHOW_MINE` | `true` | 他人主页行尾是否附注「我听了 N 次」 |
| `ASSUME_TOP_COUNT` | `0` | 设为正数则按「榜首 = N 次」换算成 `≈N次` 并给出区间 |
| `BOOT_MS` | `200` | 首次注入前的轮询间隔，抢首屏 |
| `REFRESH_MS` | `600` | 注入后的轮询间隔，只读两个节点跟 tab 切换 |
| `CACHE_MS` | `300000` | 排行数据缓存（5 分钟），切标签页不重复请求 |
| `MINE_DELAY_MS` | `600` | 首屏画上后等多久再取「我听了 N 次」，避开网页自己的排行请求 |
| `MIN_GAP_MS` | `300` | 两个接口请求之间的最小间隔 |
| `FAIL_BACKOFF_MS` | `60000` | 接口失败后多久内不再重试 |
| `MAX_USERS` | `60` | 日增量记录的账号上限，超出按最久未访问淘汰 |
| `DEBUG` | `false` | 控制台输出判定过程 |

## 数据与隐私

只存浏览器 `localStorage`，键名 `tm_w163_daily_v1`，不外传：

```json
{
  "v": 2,
  "users": {
    "1384117962": {
      "cur":  { "day": "2026-11-03", "week": { "411315632": 5 }, "all": { "411315632": 46 } },
      "base": { "day": "2026-11-02", "week": { "411315632": 2 }, "all": { "411315632": 43 } },
      "days": { "2026-11-02": { "411315632": 3 } },
      "dirty": "2026-10-15",
      "seen": 1793276935491
    }
  }
}
```

`cur` / `base` 各存两份快照（周榜反解值 + 全时间真值），`days` 只存合并后的每日增量。单人约 12KB（8 天 × ≤100 首 + 两份快照）。从 v3.4 升级时旧 `counts` 会就地翻译成 `week`，历史不丢；想重新校准，删掉这个键会重新走预热。

## 已知限制

| # | 限制 | 性质 |
| --- | --- | --- |
| 1 | 「最近一周」的绝对次数仍靠反解 | `weekData` 的 `playCount` 恒为 0，只能从 `score` 反推；「所有时间」不受影响，直接真数 |
| 2 | 漏一天访问会永久污染那条「星期几」链路 | 误差系数恒为 1，不衰减；实测漏一天后平均每首每日误差 0.32 次。数学上不可修复，脚本用 `exact` 标记提示 |
| 3 | 周榜 top100 截断 | 掉出前 100 的歌拿不到次数，这部分增量会漏 |
| 4 | 量化分辨率 = `M_w / 100` | 一周榜首 200 次时，听 1 次落在 `score=0`，不可见 |
| 5 | 周榜 `M_w ≥ 96` 不记录 | 标尺饱和，次数不可信 |
| 6 | 「我听了 N 次」只覆盖最近一周、且只在你周榜 top100 内 | 它回答「这首我也在听吗」，不是「我总共听过几次」 |
| 7 | 只在经典版页面（存在 `#m-record`）生效 | 新版 Web 播放器结构不同 |
| 8 | 两份榜单都只给 top100 | 掉出前 100 再回来那天基线断了，当天不给增量，而不是给个错数 |

## 自己验证

两条命令就能复核全文最重要的那个结论，不需要登录：

```bash
# 同一个 uid，只差 type
curl 'https://music.163.com/api/v1/play/record?uid=<任意uid>&type=0' | head -c 300
curl 'https://music.163.com/api/v1/play/record?uid=<任意uid>&type=-1' | head -c 300
```

前者 `playCount` 是 `0`，后者是真实次数。再拿 `score` 与 `max(playCount)` 验一下 `floor(playCount*100/M) === score` 是否每条都成立。

要是想看自己账号的对照，用本人 uid 更有意义 —— 同一份数据里同时有真值和 `score`，可以逐条比对。

拿返回的 `score` 跑格点反解，与 `playCount` 对比；连续观察 8 天，把「反解出的日增量」和「真实 `playCount` 的差分」并排比，就能量出这套管线的实际误差 —— 比任何模拟都可信。

旧实现归档在 [`legacy/`](./legacy)，含 2020 年原版（曾发布在 [Greasyfork](https://greasyfork.org/zh-CN/scripts/403084)，**该页已不再维护**，以本仓库为准）。它们的问题由上面的饱和定理解释：`M ≥ 97` 后反解必然退化成常数 97~99。

从 v1.0 到 v3.2 隔了六年，停更原因很简单：不管怎么改代码，`playCount` 都不会从接口里长出来，只能在错误前提上反复调参。真正解决问题的不是重写，是先花半小时读接口和页面模板 —— 确认「别人的绝对次数根本不存在」。
