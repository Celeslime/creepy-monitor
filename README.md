# 隔墙有耳 · Creepy Monitor

网易云的「听歌排行」只画条形图，不写次数。这个油猴脚本把次数补在条形图后面，并记住每个人每天新听了多少。

## 一眼看懂

排行接口带上 `type=-1`，能一次拿到「所有时间」和「最近一周」两份榜单，其中「所有时间」那份的 `playCount` 是真实次数，不登录也能请求。网页自己用的是 `type=0` 和 `type=1`，这两条路径的 `playCount` 被服务端清成 0，所以页面上只剩一根光秃秃的条。脚本改走 `-1` 取数，再把每天的快照相减，得到「今天又听了几次」。

- 显示：`46次`、`46次 +3`、`~137次`；周榜标尺太大又锚不住时，退回百分比。
- 开销：每个 uid 一条排行请求，缓存几分钟。数据只写 localStorage，不发往任何外部地址。
- 体积：完整版功能齐全；lite 只填次数，代码量小得多。
- 用法：装 Tampermonkey，粘一个文件，打开用户主页的「听歌排行」。

次数可能比你记得的大：单曲循环放一夜，一首歌就能攒下几十上百次。这个数字来自接口返回的真实 `playCount`，脚本只做搬运，不做修正。

## 安装

先装 [Tampermonkey](https://www.tampermonkey.net/)（Chrome / Edge）或 Violentmonkey（Firefox）。两个版本功能重叠，装一个就够：完整版把次数、今日增量、「我听了 N 次」、标尺锚定都做齐；lite 只填次数，不做增量也不预取，饱和时直接显示百分比。

| 版本 | 一键安装 | 源码 |
| --- | --- | --- |
| 完整版 | [安装](https://raw.githubusercontent.com/Celeslime/creepy-monitor/master/creepy-monitor.user.js) | [`creepy-monitor.user.js`](https://github.com/Celeslime/creepy-monitor/blob/master/creepy-monitor.user.js) |
| lite | [安装](https://raw.githubusercontent.com/Celeslime/creepy-monitor/master/creepy-monitor-lite.user.js) | [`creepy-monitor-lite.user.js`](https://github.com/Celeslime/creepy-monitor/blob/master/creepy-monitor-lite.user.js) |

一键安装走 raw 链接；如果打不开，就打开源码页复制全文，粘进 Tampermonkey 新建的脚本里保存。

装完打开用户主页的「听歌排行」：`https://music.163.com/#/user/home?id=xxxxxxx`。

看别人的次数不需要登录；登录只影响「我听了 N 次」，因为它得先知道你是谁。

脚本只读页面上公开的听歌排行，不改动账号、不读取私密数据；登录态只用来确认「我是谁」，取到的数据也只写进本地。

## 页面上会看到什么

脚本只加三样东西：条形后面的次数、次数后面的今日增量、他人主页行尾的一行小字。三样都能悬停看依据。

**次数**：`46次` 是真值。「所有时间」直接取 `playCount`，「最近一周」基本靠反解。标尺饱和时会退成两种形态：`~137次` 表示快照把标尺锁窄了，悬停给出 `M=134~140` 和这一行自己的区间；`86次 +12` 表示榜首的终身累计把标尺夹得够窄，次数重新变回精确。窄到只差一两个值时直接写开成 `1~2次`。连估算都站不住就只剩 `91%`，那是占榜首播放量的百分比。本人主页官方本来就显示次数，脚本不改写那个数字，只把 `+3` 挂上去，所以两种主页观感一样。

**今日增量**：`+3` 挂在次数后面，两个标签页都有。「所有时间」那份是两次真值相减，始终精确；「最近一周」那份靠反解差分加滑窗补偿，连续访问、标尺没换时同样准，漏过一天会带一份固定偏差。新进榜的歌给的是本周累计，悬停标「今日上限」。

**我听了 N 次**：只在他人主页的行尾，回答「这首我也在听吗」。要先知道你是谁，所以先问 `/api/nuser/account/get`（未登录直接跳过），再拉一次自己的周榜按歌曲 id 比对，最多两条请求，排在首屏之后，和排行请求共用一条串行队列。自己主页不显示这一段，那栏本来就是真数。

刷新方式：列表没渲染时脚本已经按 URL 里的 uid 把请求发出去了，不等 DOM。画上之后靠轮询兜底，首屏前密一点，画完放慢。切标签页时列表会重渲染，脚本靠 uid、条目数、第一行的 HTML 和注入过的痕迹组成的标记发现变化，下一轮就补上。痕迹这一项是为列表被重画回原样准备的：行数和首行都没变，只有插上去的数字没了，不带痕迹就会误判成处理过，数字再也补不回来。这里没用 MutationObserver，改用轮询加标记比对。

当前是哪个标签页不靠 DOM 判断，而是拿两套数据的 `score` 和页面上条形的实际宽度比误差，小的那份胜出。

## 数据来源

```bash
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=0' # 全部时间
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=1' # 最近一周
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=-1' # 两份一起
```

前两条每条记录长这样：`{ playCount: 0, score, song }`。

第三条返回 `{ allData, weekData }`，`allData` 里的 `playCount` 是真实次数。逐条核对过 `score = floor(playCount * 100 / M)`，M 取榜首的次数。

`weekData` 是例外：即使走 `-1`，它的 `playCount` 仍然是 0，只有 `score`。所以「最近一周」这半边还得反解。

`-1` 是网页端自己在用的参数，但清不清零终究由服务端决定。脚本每行先看 `playCount > 0` 才用真值，否则退回反解，哪天这个口子补上了也不用改代码。

## 次数怎么反解

页面模板 `textarea#m-wgt-song-listen` 里写着：

```html
<span class="bg" style='width:${x.score*100/x.max}%;'></span>
{if extData.showCount&&x.playCount}<span class="times f-ff2">${x.playCount}次</span>{/if}
```

条形宽度就是 `score`。「N次」的位置官方留好了，只是 `playCount=0` 时不渲染。脚本直接复用 `.times f-ff2` 这个类，字号和颜色都交给站点 CSS，不自己写样式。

已知一串 `score`、未知 `M`，找最小的 `M` 让每个 `score` 都能被 `floor(100*i/M)` 表达：

```js
for (let M = 1; M <= SAT_MAX; M++) {
  const lat = new Set();
  // i 从 1 起：能进榜就说明本周至少听过一次，0 次不在解空间里
  for (let i = 1; i <= M; i++) lat.add(Math.floor(100 * i / M));
  if (scores.every(s => lat.has(s))) return M;
}
```

`M` 定下来之后，每首歌的次数就是它对应的 `i`，脚本里是一张 `score → 次数` 的反查表。验证过：挑一个没饱和的标尺做盲测，解出的值与真值一致，100 首逐首零误差。

`M` 逼近 100 时格点越来越密，`M ≥ 97` 时步长不到 1.031，0 到 100 基本铺满，任何序列都能命中。所以解出来的值一旦顶到 96 以上，就说明这份榜单已经约束不住标尺了。

## 标尺饱和

饱和时页面只会出现三种结果：

- 手上有昨天的快照、能把标尺锁窄：`~137次`，悬停给出区间；
- 只定得住下界：`≥201次`；
- 连下界都定不住：`91%`。

下面是一步步收紧的过程。`M` 越大格点越密。`M ≥ 97` 时步长不到 1.031，`floor(100*i/M)` 把 0 到 100 全铺满，任何 `score` 序列都成立，解集变成 `[97, ∞)`，反解结果和真值毫无关系。

| 真实榜首次数 | 解出的 M | 结果 |
| --- | --- | --- |
| 20 / 40 / 60 / 80 | 一致 | 次数可信 |
| 100 / 300 / 3000 | 97~100 之间某个数 | 与真值无关 |

所以分界取 96。真实值一定是可行解，所以解出的 `M` 是个严格下界，饱和时先报 `≥97次` 起步。

单看一份榜单确实救不回来，但播放次数不会倒退。昨天这首歌本周是 `c`，今天窗口滑走了最老的一天（滑走量存在 `days[today-7]` 里），今天至少还有 `c` 减去滑走量，记作 `prior`。代进 `s = floor(100c/M)`：

```
M > 100 * prior / (s + 1)
```

每首歌给一个下界，取最大值。`prior` 先减 1，兜住差分踩点的误差。一首昨天 12 次、今天显示 `0%` 的歌，直接说明 `M > 1200`，`≥97次` 立刻变成 `≥1201次`。

**榜首的终身累计是现成的上界。** `allData` 里榜首那首歌的 `playCount` 是一生的累计，而周榜榜首的次数按定义就是 `M`，于是 `本周次数 ≤ 终身次数`；下界则来自 `days` 里最近 7 天的日增量之和（含今天），这 7 天正好是周榜的窗口。两者夹出的区间够窄才采信，然后从下界往上挑第一个能解释今天整份榜单的 `M`。

这条路绕开了「昨天的标尺」，不会被前一天估错连累。稀疏的 `score` 会把 `M` 解小，全场次数跟着一起缩水；但终身累计是上界、最近 7 天的累加是下界，两头一夹就能证伪那个小值，次数回到真实量级。跟着的增量来自全时间榜的真值差分，本来就不受影响，错的只是周榜那半边。

一次观测往往只定得住一段 `[M, M']`，每天各挑各的最小值，同一首歌的次数就会随榜单稀疏度上下跳（先偏小、隔天又偏大，凭空多出几十次）。所以优先沿用上次存下的 `M`，旧值还能解释今天的榜单就不换。一把稳定的尺子，比一把可能更准但会飘的尺子有用。

锚不上时，还有第二批证据：榜上没动过的歌，`prior` 就是它本周的真实次数。于是把 `M` 从下界一路扫到搜索上界，数哪个 `M` 能让最多的 `prior` 倒回自己的 `score`，吻合最多的一段就是候选区间。真实标尺一定在里面，被刷上去的那首只算一票反对，不影响多数。

| 情形 | 输出 |
| --- | --- |
| 多数 prior 能对上，区间窄 | `~137次`，悬停写 `M=134~140`，逐行还带自己的区间 |
| 窄到只差一两个值（低分档常见） | 直接写开：`1~2次` |
| 全员都在 0~1%，没有中段证据 | 不给区间，只报下界 `≥201次` |
| 今天大半的歌都在涨，prior 不再等于次数 | 一票判不了，退回百分比 |
| 中间漏过一天，或没有快照 | 滑走量算不全，退回百分比 |

低分档单独说一下：能进榜就说明本周至少听过一次，`score=0` 不等于 0 次。榜首一周 137 次时，0% 档只能是 1 次，区间收成一个点。只有榜首特别高（比如一周 500 次）时，0% 档才会是 `1~4` 次。跨度不超过 2 就写开，宽了才退回 `~N次`。

只取「最小可行 M」会被稀疏的 `score` 骗：真实 500 次、但 `score` 只落在 100/50/20/10/5 时，会解出 20 并且当成准确值。现在硬下界先把它证伪（`prior` 一对，20 明显不够），再重新锁定。

模拟过一次：60 首静止歌曲加 1 首从 40 次被刷到 137 次的歌，锁定到 `M=137~137`，60 行全部补上次数，被刷那首算出的 `+97` 与真值一致。

## 今日增量

`+3` 是两份快照相减得来的。两份榜单的 top100 交集很低，大部分歌只出现在其中一份；只算一份，另一个标签页就会空掉，所以两份都算：

| 来源 | 覆盖 | 精度 |
| --- | --- | --- |
| 全时间榜 `playCount` 真值差分 | 「所有时间」那 100 首 | 精确，两个真值直接相减 |
| 周榜反解差分 | 「最近一周」里不在全榜的歌 | 受 7 天滑窗和标尺饱和影响 |

同一首歌两边都有时取真值。周榜那份要补偿滑窗：

```
D_d = (W_d - W_{d-1}) + D_{d-7}
```

7 天前那天的增量已经滑出窗口，得加回来，这也是历史要留 8 天而不是 7 天的原因。合并后只有一张增量表，切标签页不会掉 `+n`。

补偿项有个硬约束：昨天的窗口必然包含 7 天前那一天，所以昨天的累计不可能小于那天的增量。小于就说明昨天的反解偏小了（标尺粗的时候，2 次和 3 次落在同一个 `score` 上），脚本拿那天的增量当昨天的下界再相减，否则那几首会被整个加回来，冒出「本周 2 次、今日 +3」这种自相矛盾的值。

新进榜的歌没有基线。周榜那份拿「本周累计」当今日增量，严格说是上限，但新进榜多半就是今天才开始听，值通常等于当日，悬停里写明「今日上限」。全时间那份的累计是一生的，拿 0 当基线能报出几百次，所以这类直接跳过。

还有一层：听得越杂，榜单越满。一周听过 100 首以上时，100 个位置装不下，新听的那首要排在 101 名之后，等别的歌滑出窗口才挤进来。可能过两三天才出现在榜上，脚本把它当「新进榜」，给的「本周累计 1 次」其实是几天前听的。这类账号的今日增量会系统性偏大一点，多出来的就是积压之后才进榜的那几首。接口只给前 100 名，看不到就算不出来，这部分只能认。

升级当天，全时间基线是空的（旧版本只存过周榜），这一页当天算不出增量，悬停写「基线今天才建立」，第二天恢复。

两天的快照必须用同一把尺子量。标尺每晚重解一次，换了尺子就是换了单位，相减得到的差值主要是单位位移，不是他今天听了多少。脚本给相邻两次的标尺留一点容差，超出就把周榜那半整段跳过，并记进 `dirty`（7 天后的滑窗补偿会缺这一块）。旧存储没有 `sc` 字段时，拿昨天快照里的最大值当它的标尺，否则升级后会冒出一串假增量。

精度标记只有三个条件同时满足才算 `exact`：7 天前那天的增量在手、昨天访问过、最近 8 天没漏访。漏一天之后那条链路会带一份固定偏差，数学上补不回来，只能等 8 天后自然清掉。

## 配置

脚本顶部的 `CFG`：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `MODE` | `'auto'` | `auto` 能反解就给次数，饱和时先试着锁标尺，锁不住退百分比；`count` 总是给次数（饱和时给下界）；`percent` 总是给百分比 |
| `DAILY` | `true` | 是否记录并显示今日增量 |
| `SHOW_MINE` | `true` | 他人主页行尾是否附注「我听了 N 次」 |
| `ASSUME_TOP_COUNT` | `0` | 设成正数则按「榜首 = N 次」换算成 `~N次` 并给出区间 |

其余是节奏参数：首屏与刷新轮询间隔、取「我听了 N 次」前的延迟、缓存时长、请求最小间隔、失败退避、账号上限。默认值都在脚本顶部，一般不用动。`DEBUG` 打开会在控制台打印判定过程。

另有三个常量：`SATURATION`（反解失效的分界）、`SAT_MAX`（一周次数的搜索上界）、`SAT_SLACK`（区间窄到多少才算锁定，也当跨天标尺的容差）。

## 本地存了什么

只写 localStorage 的 `tm_w163_daily_v1`，顶层是 `{ v, users }`，`users` 按 uid 存。每个用户里有：

- `cur` / `base`：今天和昨天的两份快照，各含周榜反解值 `week` 与全时间真值 `all`；
- `days`：按日期存的合并日增量；
- `dirty`：漏访或标尺漂移的标记，用来判断当天算不算精确；
- `seen`：最后访问时间，淘汰老账号时用。

快照里还会带两个辅助字段：`sc` 记当天用的是哪把尺子，`w` 是估算快照的误差半径，下次当先验时先扣掉，免得误差一轮轮放大。

单人十几 KB（8 天 × 最多 100 首 + 两份快照），账号数超过 `MAX_USERS` 后淘汰最久未访问的。从 3.4 之前的版本升上来时，旧的 `counts` 会在读取时就地翻译成 `week`，历史不丢。想重新校准，删掉这个键会重新走预热。

## 已知限制

| # | 限制 | 性质 |
| --- | --- | --- |
| 1 | 「最近一周」的绝对次数仍是反解出来的 | `weekData` 的 `playCount` 恒为 0，只能从 `score` 推；「所有时间」不受影响 |
| 2 | 漏一天访问会污染周榜那条按天相减的链路 | 误差系数恒为 1，不衰减，数学上补不回来，脚本用 `exact` 标记提示。全时间走真值差分，不受影响 |
| 3 | 两份榜单都只给 top100 | 掉出前 100 的歌拿不到次数，这天的增量会漏 |
| 4 | 量化分辨率是 `M_w / 100` | 一周榜首 200 次时，听 1 次仍落在 `score=0`，看不出来 |
| 5 | 周榜 `M_w ≥ 96` 要靠历史快照或榜首的终身累计救 | 两条路都不通（头一回访问、中间漏天、榜首不在全时间 top100）就只剩百分比 |
| 6 | 「我听了 N 次」只覆盖最近一周，且只在你周榜 top100 内 | 它回答「这首我也在听吗」，不是「我总共听过几次」 |
| 7 | 只在经典版页面生效（存在 `#m-record`） | 新版 Web 播放器结构不同 |
| 8 | 今天新进榜的歌给的是上界 | 昨天没有基线，「本周累计」可能含前几天的播放；全时间榜新进的直接跳过 |
| 9 | 听得杂的账号，新歌要排队进榜 | 一周听过 100 首以上时榜单装满，新听的那首要等别人滑出窗口，可能晚几天才上榜；那几次会记到进榜那天，今日增量因此偏大 |
