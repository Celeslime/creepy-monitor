# 隔墙有耳 · Creepy Monitor

网易云的「听歌排行」只画条形图，不写次数。这个油猴脚本把次数补在条形图后面，并记住每个人每天新听了多少。

## 一眼看懂

排行接口带上 `type=-1`，能一次拿到「所有时间」和「最近一周」两份榜单，其中「所有时间」那份的 `playCount` 是真实次数，不登录也能请求。网页自己用的是 `type=0` 和 `type=1`，这两条路径的 `playCount` 被服务端清成 0，所以页面上只剩一根光秃秃的条。脚本改走 `-1` 取数，再把每天的快照相减，得到「今天又听了几次」。

- 显示：`46次`、`46次 +3`、`~137次`；周榜标尺太大又锚不住时，退回百分比。
- 开销：每个 uid 一条请求，缓存 5 分钟。数据只写 localStorage，不发往任何外部地址。
- 体积：完整版 865 行（非空非注释 638）。只想要次数就装 lite，107 行（74）。
- 用法：装 Tampermonkey，粘一个文件，打开用户主页的「听歌排行」。

数字偶尔大得离谱，而且是真的：夜里放着歌睡着，一首歌就这么单曲循环到天亮，《蝶》在一周里转了一百多遍。脚本只负责把次数写出来，不负责劝人早睡。

## 安装

1. 装 [Tampermonkey](https://www.tampermonkey.net/)（Chrome / Edge）或 Violentmonkey（Firefox）
2. 新建脚本，把 [`creepy-monitor.user.js`](./creepy-monitor.user.js) 全文粘进去保存
   或者点 raw 链接（`raw.githubusercontent.com` 打不开就用上一种）：
   `https://raw.githubusercontent.com/Celeslime/creepy-monitor/master/creepy-monitor.user.js`
3. 打开用户主页（`https://music.163.com/#/user/home?id=xxxxxxx`），切到「听歌排行」

装 lite 版把文件名换成 `creepy-monitor-lite.user.js`。两个脚本功能重叠，装一个就够。

看别人的次数不需要登录。登录只影响「我听了 N 次」，因为它得先知道你是谁。

## 页面上会看到什么

- `46次`：真实次数。「所有时间」标签页直接取 `playCount`；「最近一周」基本靠反解。
- `46次 +3`：今天又听了 3 次。两个标签页都有。
- `~137次`：周榜标尺饱和，但昨天来过、快照还在。悬停给出 `M=134~140` 和这一行自己的区间。
- `1~2次`：区间窄到能写开，就不取约数了。
- `112次 +55`：榜首的终身累计把标尺夹得很窄，这行的次数不再是「~」。
- `91%`：占榜首播放量的百分比。饱和且没有可用快照时才出现。
- 行尾 `我听了 2 次`：你自己最近 7 天也听过这首。只在他人主页、且这首在你周榜 top100 内时显示。

本人主页官方本来就显示次数，脚本不改写那个数字，只把 `+3` 挂进去，所以两种主页观感一样。悬停都能看到这一行用的是真值、反解还是估算区间。

刷新方式：列表没渲染时脚本已经按 URL 里的 uid 把请求发出去了，不等 DOM。画上之后靠轮询兜底，首屏前 200ms 一轮，画完降到 600ms 一轮。切标签页时列表会重渲染，脚本靠 uid、行数、第一行的 HTML 组成的标记发现变化，最多 600ms 补上。这里没用 MutationObserver，早期版本在它上面抖过。

当前是哪个标签页不靠 DOM 判断，而是拿两套数据的 `score` 和页面上条形的实际宽度比误差，小的那份胜出。

## 数据来源

```bash
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=0' # 全部时间
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=1' # 最近一周
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=-1' # 两份一起
```

前两条每条记录长这样：`{ playCount: 0, score, song }`。

第三条返回 `{ allData, weekData }`，`allData` 里的 `playCount` 是真实次数。拿三个账号验过（全时间榜首分别是 2 / 49 / 397 次），`score = floor(playCount * 100 / M)` 逐条吻合，M 取榜首的次数。

`weekData` 是例外：即使走 `-1`，它的 `playCount` 仍然是 0，只有 `score`。所以「最近一周」这半边还得反解。

`-1` 是网页端自己在用的参数，但清不清零终究由服务端决定。脚本每行先看 `playCount > 0` 才用真值，否则退回反解，哪天这个口子补上了也不用改代码。

## 次数怎么反解

页面模板 `textarea#m-wgt-song-listen` 里写着：

```html
<span class="bg" style='width:${x.score*100/x.max}%;'></span>
{if extData.showCount&&x.playCount}<span class="times f-ff2">${x.playCount}次</span>{/if}
```

条形宽度就是 `score`。「N次」的位置官方留好了，只是 `playCount=0` 时不渲染。脚本直接复用 `.times f-ff2` 这个类，字号和颜色都交给站点 CSS，不自己写样式。

已知一串 `score`、未知 `M`，找最小的 `M` 让每个 `score` 都能被 `floor(100*i/M)` 表达：

```js
for (let M = 1; M <= SAT_MAX; M++) {
  const lat = new Set();
  // i 从 1 起：能进榜就说明本周至少听过一次，0 次不在解空间里
  for (let i = 1; i <= M; i++) lat.add(Math.floor(100 * i / M));
  if (scores.every(s => lat.has(s))) return M;
}
```

`M` 定下来之后，每首歌的次数就是它对应的 `i`，脚本里是一张 `score → 次数` 的反查表。只喂 `score` 盲测过一次：真实 `M=49`，解出 49，100 首逐首零误差。

`M` 逼近 100 时格点越来越密，`M ≥ 97` 时步长不到 1.031，0 到 100 基本铺满，任何序列都能命中。所以解出来的值一旦顶到 96 以上，就说明这份榜单已经约束不住标尺了。

## 标尺饱和

`M` 越大格点越密。`M ≥ 97` 时步长不到 1.031，`floor(100*i/M)` 把 0 到 100 全铺满，任何 `score` 序列都成立，解集变成 `[97, ∞)`，反解结果和真值毫无关系。

| 真实榜首次数 | 解出的 M | 结果 |
| --- | --- | --- |
| 20 / 40 / 60 / 80 | 一致 | 次数可信 |
| 100 / 300 / 3000 | 97~100 之间某个数 | 与真值无关 |

所以分界取 96。真实值一定是可行解，所以解出的 `M` 是个严格下界，饱和时先报 `≥97次` 起步。

单看一份榜单确实救不回来，但播放次数不会倒退。昨天这首歌本周是 `c`，今天窗口滑走了最老的一天（滑走量存在 `days[today-7]` 里），今天至少还有 `c` 减去滑走量，记作 `prior`。代进 `s = floor(100c/M)`：

```
M > 100 * prior / (s + 1)
```

每首歌给一个下界，取最大值。`prior` 先减 1，兜住差分踩点的误差。一首昨天 12 次、今天显示 `0%` 的歌，直接说明 `M > 1200`，`≥97次` 立刻变成 `≥1201次`。

**榜首的终身累计是现成的上界。** `allData` 里榜首那首歌的 `playCount` 是一生的累计，而周榜榜首的次数按定义就是 `M`，于是 `本周次数 ≤ 终身次数`；下界则来自 `days` 里最近 7 天的日增量之和（含今天），这 7 天正好是周榜的窗口。区间收到 `max(3, hi·5%)` 以内才采信，然后从下界往上挑第一个能解释今天整份榜单的 `M`。

这条路绕开了「昨天的标尺」，不会被前一天估错连累。《蝶》那次被假标尺算成 89 次，但它的终身累计只有 112 上下、最近 7 天的日增量也对得上，锚定把 `M` 收到 112~114，那一行于是回到 `112次`；跟着的 `+55` 本来就是全时间榜的真值差分，不用动。

一次观测往往只定得住一段 `[M, M']`，每天各挑各的最小值，同一首歌的次数就会随榜单稀疏度上下跳（昨天 38、今天 89，凭空多出 51 次）。所以优先沿用上次存下的 `M`，旧值还能解释今天的榜单就不换。一把稳定的尺子，比一把可能更准但会飘的尺子有用。

锚不上时，还有第二批证据：榜上没动过的歌，`prior` 就是它本周的真实次数。于是把 `M` 从下界扫到 2000，数哪个 `M` 能让最多的 `prior` 倒回自己的 `score`，吻合最多的一段就是候选区间。真实标尺一定在里面，被刷上去的那首只算一票反对，不影响多数。

| 情形 | 输出 |
| --- | --- |
| 多数 prior 能对上，区间窄 | `~137次`，悬停写 `M=134~140`，逐行还带自己的区间 |
| 窄到只差一两个值（低分档常见） | 直接写开：`1~2次` |
| 全员都在 0~1%，没有中段证据 | 不给区间，只报下界 `≥201次` |
| 今天大半的歌都在涨，prior 不再等于次数 | 一票判不了，退回百分比 |
| 中间漏过一天，或没有快照 | 滑走量算不全，退回百分比 |

低分档单独说一下：能进榜就说明本周至少听过一次，`score=0` 不等于 0 次。榜首一周 137 次时，0% 档只能是 1 次，区间收成一个点。只有榜首特别高（比如一周 500 次）时，0% 档才会是 `1~4` 次。跨度不超过 2 就写开，宽了才退回 `~N次`。

顺带修了个老问题：只取「最小可行 M」会被稀疏的 `score` 骗。真实 500 次、但 `score` 只落在 100/50/20/10/5 时，会解出 20 并且当成准确值。现在硬下界先把它证伪（`prior` 一对，20 明显不够），再重新锁定。

模拟过一次：60 首静止歌曲加 1 首从 40 次被刷到 137 次的歌，锁定到 `M=137~137`，60 行全部补上次数，被刷那首算出的 `+97` 与真值一致。

## 今日增量

实测两个账号，「最近一周」和「所有时间」的 top100 交集只有 13/100 和 4/100。只算一份，另一个标签页就会空掉，所以两份都算：

| 来源 | 覆盖 | 精度 |
| --- | --- | --- |
| 全时间榜 `playCount` 真值差分 | 「所有时间」那 100 首 | 精确，两个真值直接相减 |
| 周榜反解差分 | 「最近一周」里不在全榜的歌 | 受 7 天滑窗和标尺饱和影响 |

同一首歌两边都有时取真值。周榜那份要补偿滑窗：

```
D_d = (W_d - W_{d-1}) + D_{d-7}
```

7 天前那天的增量已经滑出窗口，得加回来，这也是历史要留 8 天而不是 7 天的原因。合并后只有一张增量表，切标签页不会掉 `+n`。

新进榜的歌没有基线。周榜那份拿「本周累计」当今日增量，严格说是上限，但新进榜多半就是今天才开始听，值通常等于当日，悬停里写明「今日上限」。全时间那份的累计是一生的，拿 0 当基线能报出几百次，所以这类直接跳过。

升级当天，全时间基线是空的（旧版本只存过周榜），这一页当天算不出增量，悬停写「基线今天才建立」，第二天恢复。

两天的快照必须用同一把尺子量。标尺每晚重解一次，换了尺子就是换了单位，相减得到的差值主要是单位位移，不是他今天听了多少。脚本给相邻两次的标尺留 5% 容差，超出就把周榜那半整段跳过，并记进 `dirty`（7 天后的滑窗补偿会缺这一块）。旧存储没有 `sc` 字段时，拿昨天快照里的最大值当它的标尺，否则升级后会冒出一串 `+13 +8 +8` 的假增量。

精度标记只有三个条件同时满足才算 `exact`：7 天前那天的增量在手、昨天访问过、最近 8 天没漏访。漏一天之后那条链路会带固定误差（实测平均每首每天 0.32 次），数学上补不回来，只能等 8 天后自然清掉。

## 「我听了 N 次」

`play/record` 对本人返回真实 `playCount`，所以先问 `/api/nuser/account/get`（未登录返回 `account: null`，直接跳过），再拉一次自己的周榜 `type=1`，按歌曲 id 比对。

最多两条请求，排在首屏之后（`MINE_DELAY_MS`，默认 600ms），和排行请求共用一条串行队列，不跟网页抢。自己主页不显示这一段，那栏本来就是真数。

## 配置

脚本顶部的 `CFG`：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `MODE` | `'auto'` | `auto` 能反解就给次数，饱和时先试着锁标尺，锁不住退百分比；`count` 总是给次数（饱和时给下界）；`percent` 总是给百分比 |
| `DAILY` | `true` | 是否记录并显示今日增量 |
| `SHOW_MINE` | `true` | 他人主页行尾是否附注「我听了 N 次」 |
| `ASSUME_TOP_COUNT` | `0` | 设成正数则按「榜首 = N 次」换算成 `~N次` 并给出区间 |
| `BOOT_MS` | `200` | 首屏画上之前的轮询间隔 |
| `REFRESH_MS` | `600` | 画上之后的轮询间隔，只用来跟标签页切换 |
| `CACHE_MS` | `300000` | 排行数据缓存（5 分钟），切标签页不重复请求 |
| `MINE_DELAY_MS` | `600` | 首屏画上后等多久再取「我听了 N 次」 |
| `MIN_GAP_MS` | `300` | 两个接口请求的最小间隔 |
| `FAIL_BACKOFF_MS` | `60000` | 接口失败后多久内不再重试 |
| `MAX_USERS` | `60` | 增量记录的账号上限，超出按最久未访问淘汰 |
| `DEBUG` | `false` | 控制台打印判定过程 |

另外三个是常量，一般不用动：`SATURATION = 96`（反解失效的分界）、`SAT_MAX = 2000`（一周次数的搜索上界）、`SAT_SLACK = 0.05`（锁定或锚定出来的区间宽于 5% 就不算锁定，只报下界；跨天比对标尺也拿它当容差）。

## 本地存了什么

只写 localStorage 的 `tm_w163_daily_v1`：

```json
{
  "v": 2,
  "users": {
    "1384117962": {
      "cur": { "day": "2026-11-03", "week": { "411315632": 5 }, "all": { "411315632": 46 },
        "sc": { "lo": 112, "hi": 112 } },
      "base": { "day": "2026-11-02", "week": { "411315632": 2 }, "all": { "411315632": 43 },
        "sc": { "lo": 112, "hi": 112 } },
      "days": { "2026-11-02": { "411315632": 3 } },
      "dirty": "2026-10-15",
      "seen": 1793276935491
    }
  }
}
```

`cur` / `base` 各存两份快照（周榜反解值 + 全时间真值），`days` 只存合并后的日增量。`sc` 记着那天用的是哪把尺子（`hi` 为 `null` 表示只定住了下界），第二天拿它比对，也拿它当先验。估算出来的那次快照会多一个 `w`，表示误差半径 ±N 次，下次当先验时先扣掉，免得误差一轮轮放大。

单人十几 KB（8 天 × 最多 100 首 + 两份快照），账号上限 60，超出按最久未访问淘汰。从 3.4 之前的版本升上来时，旧的 `counts` 会在读取时就地翻译成 `week`，历史不丢。想重新校准，删掉这个键会重新走预热。

## 已知限制

| # | 限制 | 性质 |
| --- | --- | --- |
| 1 | 「最近一周」的绝对次数仍是反解出来的 | `weekData` 的 `playCount` 恒为 0，只能从 `score` 推；「所有时间」不受影响 |
| 2 | 漏一天访问会污染周榜那条按天相减的链路 | 误差系数恒为 1，不衰减，实测漏一天后平均每首每天差 0.32 次。数学上补不回来，脚本用 `exact` 标记提示。全时间走真值差分，不受影响 |
| 3 | 两份榜单都只给 top100 | 掉出前 100 的歌拿不到次数，这天的增量会漏 |
| 4 | 量化分辨率是 `M_w / 100` | 一周榜首 200 次时，听 1 次仍落在 `score=0`，看不出来 |
| 5 | 周榜 `M_w ≥ 96` 要靠历史快照或榜首的终身累计救 | 两条路都不通（头一回访问、中间漏天、榜首不在全时间 top100）就只剩百分比 |
| 6 | 「我听了 N 次」只覆盖最近一周，且只在你周榜 top100 内 | 它回答「这首我也在听吗」，不是「我总共听过几次」 |
| 7 | 只在经典版页面生效（存在 `#m-record`） | 新版 Web 播放器结构不同 |
| 8 | 今天新进榜的歌给的是上界 | 昨天没有基线，「本周累计」可能含前几天的播放；全时间榜新进的直接跳过 |

## 自己核对

不需要登录，两条命令就能复核最关键的结论：

```bash
curl 'https://music.163.com/api/v1/play/record?uid=<任意uid>&type=0' | head -c 300
curl 'https://music.163.com/api/v1/play/record?uid=<任意uid>&type=-1' | head -c 300
```

前者 `playCount` 是 0，后者是真数。再拿 `score` 和 `max(playCount)` 验一下每条是否都满足 `floor(playCount*100/M) === score`。

想看反解的真实误差，用本人 uid 更有意义：同一份数据里既有真值又有 `score`，可以逐条比对。连续观察 8 天，把「反解出的日增量」和「真实 `playCount` 的差分」并排列出来，就能量出这套管线在你账号上的实际偏差。
