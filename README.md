# 隔墙有耳 · Creepy Monitor

网易云的「听歌排行」只画条形图，不写次数。这个油猴脚本把次数补在条形图后面，并记住每个人每天新听了多少。

## 一眼看懂

排行接口带上 `type=-1`，能一次拿到「所有时间」和「最近一周」两份榜单，其中「所有时间」那份的 `playCount` 是真实次数，不登录也能请求。网页自己用的是 `type=0` 和 `type=1`，这两条路径的 `playCount` 被服务端清成 0，所以页面上只剩一根光秃秃的条。脚本改走 `-1` 取数，再把每天的快照相减，得到「今天又听了几次」。

- 显示：`46次`、`46次 +3`、`137~140次`；周榜标尺太粗、周围又凑不出唯一解释时，退回百分比（悬停里仍写着大约多少次）。页头「累积听歌 N 首」后面还会挂一个「今天新听了几首」，那是另一条线，不依赖排行。
- 开销：每个 uid 一条排行请求，缓存几分钟。数据只写 localStorage，不发往任何外部地址。
- 体积：完整版功能齐全；lite 只填次数，代码量小得多。
- 用法：装 Tampermonkey，粘一个文件，打开用户主页的「听歌排行」。

次数可能比你记得的大：单曲循环放一夜，一首歌就能攒下几十上百次。这个数字来自接口返回的真实 `playCount`，脚本只做搬运，不做修正。

## 页面上会看到什么

脚本只加四样东西：条形后面的次数、次数后面的今日增量、他人主页行尾的一行小字、页头累积听歌数后面的今天新听。四样都能悬停看依据。

**次数**：`46次` 是真值。「所有时间」直接取 `playCount`，「最近一周」基本靠反解。反解说不出唯一解时会退成三种形态：`137~140次` 表示快照把标尺锁窄了，悬停给出区间依据；`86次 +12` 表示榜首的终身累计把标尺夹得够窄，次数重新变回精确；连估算都站不住就只剩 `91%`，那是占榜首播放量的百分比，悬停里仍会写「按最小可行标尺推大约多少次」。本人主页官方本来就显示次数，脚本不改写那个数字，只把 `+3` 挂上去，所以两种主页观感一样。

**今日增量**：`+3` 挂在次数后面，两个标签页都有。「所有时间」那份是两次真值相减，始终精确；「最近一周」那份靠反解差分加滑窗补偿，连续访问时同样准，标尺换了照样算（可能差一格），漏过一天会带一份固定偏差。新进榜的歌给的是本周累计，悬停标「今日上限」。

**我听了 N 次**：只在他人主页的行尾，回答「这首我也在听吗」。要先知道你是谁，所以先问 `/api/nuser/account/get`（未登录直接跳过），再拉一次自己的周榜按歌曲 id 比对，最多两条请求，排在首屏之后，和排行请求共用一条串行队列。这份周榜必须单独取 `type=1`：排行的缓存走 `type=-1`，它的 `weekData.playCount` 被清成 0，混用会一首歌都取不到。id 对不上时再按「歌名 + 首位歌手」认一次 —— 同一场录音常常挂着两个 id（单曲版、专辑版），只按 id 会整行空着。自己主页不显示这一段，那栏本来就是真数。

**今天新听了 N 首**：页头那行「累积听歌 3751 首」是注册以来听过多少首不同的歌，按歌曲计、不按次数。这个数只增不减，把上次记下的值留下来相减，差值就是这期间第一次听到的歌有几首。它和排行那套差分互不相干：排行只给 top100，这一条不挑歌，能回答「今天碰到几首没听过的」。数字直接读页面上那行，不额外发请求；接口里同一个值叫 `listenSongs`，只是用来核对语义。头一天只存基线不显示，同一天再看会跟着变大，隔几天才来看则摊成那几天的合计，悬停里写明天数。

刷新方式：列表没渲染时脚本已经按 URL 里的 uid 把请求发出去了，不等 DOM。画上之后靠轮询兜底，首屏前密一点，画完放慢。切标签页时列表会重渲染，脚本靠 uid、条目数、第一行的 HTML 和注入过的痕迹组成的标记发现变化，下一轮就补上。痕迹这一项是为列表被重画回原样准备的：行数和首行都没变，只有插上去的数字没了，不带痕迹就会误判成处理过，数字再也补不回来。这里没用 MutationObserver，改用轮询加标记比对。

当前是哪个标签页不靠 DOM 判断，而是拿两套数据的 `score` 和页面上条形的实际宽度比误差，小的那份胜出。

## 数据来源

```bash
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=0' # 全部时间
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=1' # 最近一周
curl 'https://music.163.com/api/v1/play/record?uid=xxxx&type=-1' # 两份一起
```

前两条每条记录长这样：`{ playCount: 0, score, song }`。

第三条返回 `{ allData, weekData }`，`allData` 里的 `playCount` 是真实次数。逐条核对过 `score = floor(playCount * 100 / M)`，M 取榜首的次数。

`weekData` 是例外：即使走 `-1`，它的 `playCount` 仍然是 0，只有 `score`。所以「最近一周」这半边还得反解。

`-1` 是网页端自己在用的参数，但清不清零终究由服务端决定。脚本每行先看 `playCount > 0` 才用真值，否则退回反解，哪天这个口子补上了也不用改代码。

## 次数怎么反解

页面模板 `textarea#m-wgt-song-listen` 里写着：

```html
<span class="bg" style='width:${x.score*100/x.max}%;'></span>
{if extData.showCount&&x.playCount}<span class="times f-ff2">${x.playCount}次</span>{/if}
```

条形宽度就是 `score`。「N次」的位置官方留好了，只是 `playCount=0` 时不渲染。脚本直接复用 `.times f-ff2` 这个类，字号和颜色都交给站点 CSS，不自己写样式。

已知一串 `score`、未知 `M`，找最小的 `M` 让每个 `score` 都能被 `floor(100*i/M)` 表达：

```js
for (let M = 1; M <= SAT_MAX; M++) {
  const lat = new Set();
  // i 从 1 起：能进榜就说明本周至少听过一次，0 次不在解空间里
  for (let i = 1; i <= M; i++) lat.add(Math.floor(100 * i / M));
  if (scores.every(s => lat.has(s))) return M;
}
```

`M` 定下来之后，每首歌的次数就是它对应的 `i`，脚本里是一张 `score → 次数` 的反查表。验证过：挑一个没饱和的标尺做盲测，解出的值与真值一致，100 首逐首零误差。

`M` 逼近 100 时格点越来越密，`M ≥ 97` 时步长不到 1.031，0 到 100 基本铺满，任何序列都能命中。所以解出来的值一旦顶到 96 以上，就说明这份榜单已经约束不住标尺了。

## 标尺饱和

**「能解出来」和「解出来的是真的」是两回事。** 上面那个循环永远能返回一个值，因为 `M` 够大时格点必然铺满；它返回的只是「能解释这份榜单的最小标尺」，真实标尺可能大得多。

判据是这个：**`M0` 往后 10% 以内，还有没有别的标尺也能解释同一份榜单？**

有，说明这份榜单在这个尺度上根本分不出两个值 —— 实测过一份真值 127 的榜单，`M=89` 和 `M=127` 都能解释它，逐首歌差 40%。没有，说明 `M0` 被格点钉住了。

10% 这条线是从两头量出来的：完整榜（每首都进榜）时，最近的另一个可行标尺至少差 19%；截断成 top100 的稀疏榜常常只差 1~6%。中间是空的，所以取 10%。

分三条路：

- 格点细、附近也没有第二种解释 → 写次数（`46次`）；
- 手上有先验能把标尺锁进 5% 的窄区间 → 写区间（`137~140次`）或区间的点值；
- 剩下的一律显示 `91%`（占榜首播放量），悬停里给「按最小可行标尺推大约多少次」。

下面是一步步收紧的过程。

| 真实榜首次数 | 解出的 M | 结果 |
| --- | --- | --- |
| 20 / 40 / 60 / 80 | 一致 | 次数可信 |
| 89 / 127 | 89 | 附近没有第二种解释时才是这个值 |
| 100 / 300 / 3000 | 97~100 之间某个数 | 与真值无关 |

真实值一定是可行解，所以解出的 `M` 是个严格下界。

## 四条证据求交

每次观测，脚本手上有一堆证据，各自只说「`M` 落在哪一段」，最后取交集。硬证据互相矛盾就整条放弃；软证据跟硬结论冲突时丢掉它，而不是反过来改硬结论。

| 证据 | 区间 | 硬？ | 来源 |
| --- | --- | --- | --- |
| 格点反解 | `[M0, ∞)` | 硬 | 真实标尺一定让每个 `score` 都能命中 |
| 榜首的终身累计 | `[1, 终身次数]` | 硬 | 本周次数不可能超过一生累计 |
| 榜首缺席全时间榜 | `[1, 榜尾值]` | 硬 | 榜固定 100 条，缺席等于终身不到榜尾 |
| 最近 7 天的累加 | `[和, ∞)` | 软 | `days` 里那串日增量 |
| 播放不倒退 | `[hard, ∞)` | 软 | 昨天的次数减去窗口滑出量 |
| prior 命中段 | `[lo, hi]` | 软 | 没动过的那批歌，prior 就是本周次数 |

`hard` 是「昨天这首歌本周是 `c`，今天窗口滑走了最老的一天，今天至少还有 `c` 减去滑走量」推出来的：代进 `s = floor(100c/M)` 得 `M > 100·prior/(s+1)`，逐首取最大，`prior` 先减 1 兜住差分踩点的误差。一首昨天 12 次、今天显示 `0%` 的歌直接说明 `M > 1200`。

「榜首的终身累计」和「榜首缺席」这两条最有用的地方是证伪：某首歌本周被算成 175 次、终身却连榜尾的 56 次都不到，那就说明尺子放大了，而不是歌听得多。

求交之后按这个顺序取值：

1. 反解在饱和线以下（`M0 < 96`）→ 用 `M0`，但先跑一遍上面的 10% 判据；
2. 交集能收窄到 5% 以内 → 用这个区间，区间里逐首取 `prior`（落在带里就说明今天没动）；
3. 收不窄、但上次存的 `M` 落在交集里而且能解释今天的榜单 → 沿用上次的尺子；
4. 都不行 → 拿交集下界当点估计，明说只是下界。

**沿用只排在第 3 位，这一点是拿 bug 换来的。** 反解能定住标尺时它就是硬下界，真实值不会比它小，让沿用去顶它就再也纠不回来：判据「旧值还能解释今天的榜单」对放大的尺子永远成立（可行集本来就是 `[M, ∞)`），一把被写错的 `M` 会借着它一路传下去。踩过的坑是一把 56 被存进快照后每天自洽地沿用，而真实值只有 28。

反过来，一次观测往往只定得住一段 `[M, M']`，每天各挑各的最小值，同一首歌的次数就会随榜单稀疏度上下跳（先偏小、隔天又偏大，凭空多出几十次）。所以反解不可辨识时，一把稳定的旧尺子比一把可能更准但会飘的新尺子有用 —— 这就是第 3 条存在的理由。

这套结构的好处是**加证据不用再改别人**：以后想到新约束，就是多交一个区间，不用回头调顺序。`resolveWeek` 返回的 `scale.why` 记着这次走了哪条路（`solve` / `lock:pin` / `lock:anchor` / `prev` / `lower`），出问题时先看它。

跟着的增量来自全时间榜的真值差分，本来就不受影响，错的只是周榜那半边。

反解不可用时，沿用之前要先过一道上面的硬上界，越过就作废、回落到反解最小值。同理，用先验推出来的下界如果越过了它，说明错的是先验，那一条路整段放弃，不拿它去 pin 标尺 —— 否则一把错尺子会被自己的先验反复确认，再也下不来。

锚不上时，还有第二批证据：榜上没动过的歌，`prior` 就是它本周的真实次数。于是把 `M` 从下界一路扫到上界（有硬上界就扫到硬上界），数哪个 `M` 能让最多的 `prior` 倒回自己的 `score`，吻合最多的一段就是候选区间。真实标尺一定在里面，被刷上去的那首只算一票反对，不影响多数。

| 情形 | 输出 |
| --- | --- |
| 多数 prior 能对上，区间窄 | `~137次`，悬停写 `M=136~141`，逐行还带自己的区间 |
| 窄到只差一两个值（低分档常见） | 直接写开：`1~2次` |
| 全员都在 0~1%，没有中段证据 | 凑不出命中段，退回百分比 |
| 今天大半的歌都在涨，prior 不再等于次数 | 一票判不了，退回百分比 |
| 中间漏过一天，或没有快照 | 滑走量算不全，退回百分比 |

低分档单独说一下：能进榜就说明本周至少听过一次，`score=0` 不等于 0 次。榜首一周 137 次时，0% 档只能是 1 次，区间收成一个点。只有榜首特别高（比如一周 500 次）时，0% 档才会是 `1~4` 次。跨度不超过 2 就写开，宽了才退回 `~N次`。

只取「最小可行 M」会被稀疏的 `score` 骗：真实 500 次、但 `score` 只落在 100/50/20/10/5 时，会解出 20 并且当成准确值。现在硬下界先把它证伪（`prior` 一对，20 明显不够），再重新锁定。

模拟过一次：60 首静止歌曲加 1 首从 40 次被刷到 137 次的歌，锁定到 `M=136~138`（命中段两端各留 1 次），60 行全部补上次数，被刷那首算出的 `+97` 与真值一致。

## 今日增量

`+3` 是两份快照相减得来的。两份榜单的 top100 交集很低，大部分歌只出现在其中一份；只算一份，另一个标签页就会空掉，所以两份都算：

| 来源 | 覆盖 | 精度 |
| --- | --- | --- |
| 全时间榜 `playCount` 真值差分 | 「所有时间」那 100 首 | 精确，两个真值直接相减 |
| 周榜反解差分 | 「最近一周」里不在全榜的歌 | 受 7 天滑窗和标尺饱和影响 |

同一首歌两边都有时取真值。周榜那份要补偿滑窗：

```
D_d = (W_d - W_{d-1}) + D_{d-7}
```

7 天前那天的增量已经滑出窗口，得加回来，这也是历史要留 8 天而不是 7 天的原因。合并后只有一张增量表，切标签页不会掉 `+n`。

补偿项有个硬约束：昨天的窗口必然包含 7 天前那一天，所以昨天的累计不可能小于那天的增量。小于就说明昨天的反解偏小了（标尺粗的时候，2 次和 3 次落在同一个 `score` 上），脚本拿那天的增量当昨天的下界再相减，否则那几首会被整个加回来，冒出「本周 2 次、今日 +3」这种自相矛盾的值。

新进榜的歌没有基线。周榜那份拿「本周累计」当今日增量，严格说是上限，但新进榜多半就是今天才开始听，值通常等于当日，悬停里写明「今日上限」。全时间那份的累计是一生的，拿 0 当基线能报出几百次，所以这类直接跳过。

还有一层：听得越杂，榜单越满。一周听过 100 首以上时，100 个位置装不下，新听的那首要排在 101 名之后，等别的歌滑出窗口才挤进来。可能过两三天才出现在榜上，脚本把它当「新进榜」，给的「本周累计 1 次」其实是几天前听的。这类账号的今日增量会系统性偏大一点，多出来的就是积压之后才进榜的那几首。接口只给前 100 名，看不到就算不出来，这部分只能认。

升级当天，全时间基线是空的（旧版本只存过周榜），这一页当天算不出增量，悬停写「基线今天才建立」，第二天恢复。

标尺每晚重解一次，换了尺子是不是就不能相减，取决于那天的次数定没定死。区间退化成一个点，说明那天是精确反解，每首歌的次数就是真实次数本身 —— 榜首今天多听了 7 次把 `M` 从 29 顶到 36，别人的次数并不因此改变，相减照样成立，只是那一格可能差一次，悬停里写「标尺从 29 变成 36，可能差一格」。只有靠先验锁在一段区间里的标尺（`lo ≠ hi`），次数本身不唯一，才整段跳过并记进 `dirty`（7 天后的滑窗补偿会缺这一块）。旧存储没有 `sc` 字段时，既拿昨天快照里的最大值当它的标尺，也当作「定没定死不可知」，保守地按跳过处理。

精度标记只有三个条件同时满足才算 `exact`：7 天前那天的增量在手、昨天访问过、最近 8 天没漏访。漏一天之后那条链路会带一份固定偏差，数学上补不回来，只能等 8 天后自然清掉。

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `MODE` | `'auto'` | `auto` 能反解就给次数，饱和时先试着锁标尺，锁不住退百分比；`count` 总是给次数（饱和时给下界）；`percent` 总是给百分比 |
| `DAILY` | `true` | 是否记录并显示今日增量（页头的「今天新听」也归它管） |
| `SHOW_MINE` | `true` | 他人主页行尾是否附注「我听了 N 次」 |
| `ASSUME_TOP_COUNT` | `0` | 设成正数则按「榜首 = N 次」换算成 `~N次` 并给出区间 |

其余是节奏参数：首屏与刷新轮询间隔、取「我听了 N 次」前的延迟、缓存时长、请求最小间隔、失败退避、账号上限。默认值都在脚本顶部，一般不用动。`DEBUG` 打开会在控制台打印判定过程。

另有四个常量：`SATURATION`（反解必然失效的分界，96）、`DENSE`（格点粗到可能误导的分界，91）、`AMBIGUOUS`（`M0` 往后多近还有别的解释就不算解出来，0.1）、`SAT_SLACK`（区间窄到多少才算锁定，也当跨天标尺的容差）。`SAT_MAX` 是一周次数的搜索上界。

## 本地存了什么

只写 localStorage 的 `tm_w163_daily_v1`，顶层是 `{ v, users }`，`users` 按 uid 存。每个用户里有：

- `cur` / `base`：今天和昨天的两份快照，各含周榜反解值 `week` 与全时间真值 `all`；
- `days`：按日期存的合并日增量；
- `head`：页头累计听歌数的上次记录（`base` 是上次跨天时的值，`n` 是最近一次看到的值）；
- `dirty`：漏访或标尺漂移的标记，用来判断当天算不算精确；
- `seen`：最后访问时间，淘汰老账号时用。

快照里还会带两个辅助字段：`sc` 记当天用的是哪把尺子，`w` 是估算快照的误差半径，下次当先验时先扣掉，免得误差一轮轮放大。

单人十几 KB（8 天 × 最多 100 首 + 两份快照），账号数超过 `MAX_USERS` 后淘汰最久未访问的。从 3.4 之前的版本升上来时，旧的 `counts` 会在读取时就地翻译成 `week`，历史不丢。想重新校准，删掉这个键会重新走预热。

## 已知限制

| # | 限制 | 性质 |
| --- | --- | --- |
| 1 | 「最近一周」的绝对次数仍是反解出来的 | `weekData` 的 `playCount` 恒为 0，只能从 `score` 推；「所有时间」不受影响 |
| 2 | 漏一天访问会污染周榜那条按天相减的链路 | 误差系数恒为 1，不衰减，数学上补不回来，脚本用 `exact` 标记提示。全时间走真值差分，不受影响 |
| 3 | 两份榜单都只给 top100 | 掉出前 100 的歌拿不到次数，这天的增量会漏 |
| 4 | 量化分辨率是 `M_w / 100` | 一周榜首 200 次时，听 1 次仍落在 `score=0`，看不出来 |
| 5 | 周榜 `M_w ≥ 91` 要靠历史快照或榜首的终身累计救 | 两条路都不通（头一回访问、中间漏天、榜单不满 100 条且榜首缺席）就只剩百分比 |
| 6 | 次数可能偏小，不会偏大 | 榜单 `score` 稀疏时反解只能给出下界（最小可行 `M`），拿它算的次数是保守值；偏小只是少报，不会凭空多出几十次 |
| 7 | 标尺跳变那天可能差一格 | 两天都是精确反解时照常相减，但格点变了，某首歌的差值可能多算或少算一次；悬停会说明标尺从多少变成多少。要是两天的次数都只锁在区间里（`lo ≠ hi`），这天仍然整段空着，滑窗补偿链因此有一周是残的 |
| 8 | 「我听了 N 次」只覆盖最近一周，且只在你周榜 top100 内 | 它回答「这首我也在听吗」，不是「我总共听过几次」；榜单外没有任何接口能查到，同名版本靠歌名认，标题一样歌手一样但其实是另一段录音时可能认错 |
| 9 | 只在经典版页面生效（存在 `#m-record`） | 新版 Web 播放器结构不同 |
| 10 | 今天新进榜的歌给的是上界 | 昨天没有基线，「本周累计」可能含前几天的播放；全时间榜新进的直接跳过 |
| 11 | 听得杂的账号，新歌要排队进榜 | 一周听过 100 首以上时榜单装满，新听的那首要等别人滑出窗口，可能晚几天才上榜；那几次会记到进榜那天，今日增量因此偏大 |
| 12 | 「今天新听」要连着看才有值 | 头一天只存基线；隔了几天才来看，差值摊成那几天的合计，悬停里写明天数。它读的是页头那行文字（`#rHeader h4`），站点改排版就失效 |
| 13 | `M` 越大能显示次数的人越少 | `M ≥ 91` 的账号（一周榜首听九十多次以上）几乎全程显示百分比，只有先验恰好把标尺锁进窄区间时才给数。这是信息量的天花板：榜单在这个尺度上分不出两个值，硬给数字就是编。仿真的 heavy 画像里 2100 行只有 200 行拿到次数 |
| 14 | 偶尔一整天的次数全偏小 5~10% | 锁定时用的 prior 本身是估的，命中段可能整体偏一格。区间两端各留了 1 次余量，`npm run sim` 的 150 个虚拟账号里没有一行越界，但真碰上极端稀疏的榜单仍可能差几次 |

## 测试

仓库自带两套检查，纯 Node，不需要浏览器：

| 命令 | 覆盖 |
| --- | --- |
| `npm test` | 191 条断言、12 个套件：DOM 注入结构、滑窗补偿、标尺决策、标尺歧义、标尺跳变、锚定上界、页头计数、「我听了 N 次」、同名异 id、重画补回、真实快照回放、两版纯函数一致性 |
| `npm run sim` | 随机仿真：造虚拟账号 → 按站点公式生成榜单 → 逐日喂给脚本 → 拿「我让它听了几次」当标准答案 |
| `npm run verify` | 两个都跑，提交前用这个 |

`test/fixtures/snapshot-169.json` 是 2026-11-14 那次「整页增量消失」的现场（裁掉了与结论无关的字段），`test/replay-169.js` 拿它当回归语料：改了标尺或差分逻辑，这里必须仍然算出那六行、合计 +20 次。

仿真有四个画像（casual / normal / wide / heavy）加随机漏访，默认 6 个账号 × 24 天，0.3 秒跑完。它只认三条硬约定：

1. **只要页面写成「N次」，就必须真的等于 N**（`≥`、`~`、`%` 不在此列）；
2. 写成 `a~b次` 的，真值可以落在区间外 5% 以内（两端都是估出来的），超出去算错；
3. `今日增量 ≤ 本周累计` 这类不变式，任何画像下都不能破。

第 1 条是这套测试最值钱的地方：它不认「大约对」，只认「确实对」。`npm run sim -- --accounts 6 --days 30 --seed N` 换种子跑，25 个种子（150 个账号）现在零违规。

饱和区那批偏差以前是 `--strict` 的靶子（627 行把估算写成精确值）。v3.8 的 10% 判据落地后降到 0 —— 代价是 heavyweight 画像里 2100 行只剩 200 行拿到次数，其余显示百分比。

```bash
node test/sim.js --accounts 20 --days 40 --seed 7 --verbose
node test/sim.js --dump 24 # 打印那天周榜的 score 序列，方便离线复现某一行
```
